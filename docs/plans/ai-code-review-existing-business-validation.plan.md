## Objective

驗證並在必要時改善 `ai-code-review`，使其能支援**同一個舊專案改用新架構、功能陸續移轉至新專案**的審查：每一批以固定的舊專案業務行為為基準，確認本批應移轉的規則、例外及副作用完整且一致，同時確認本批沒有破壞先前已移轉的功能。

審查應支援三個決策：本批可否接受、哪些規則仍不一致或缺證、整體移轉還有哪些功能待完成。架構、類別、方法、資料模型與呼叫方式可以改變；未核准的業務行為差異不可因「改架構」而被默認接受。

先對目前 skill 做情境驗證，只有實際失敗支持時才作最小修正。目標是可追溯、限定範圍的業務一致性判斷，不宣稱 code review 能證明所有輸入或整個系統絕對等價。

## Background

使用者已澄清：新專案承接的是舊專案逐步移轉的功能；新專案中的既有功能主要是先前批次已移轉的內容。前版以「另一套既有業務接收外來功能」為中心的情境已被本定義取代。

目前 skill 已有舊規則先行、多對多映射、caller／副作用追蹤及限定範圍 PASS／FAIL／UNKNOWN。待驗證的是這些要求能否在**分批改架構**時落實，尤其是本批規則漏搬、架構拆分改變副作用、跨批相依、已移轉功能回歸及累積進度判斷。不能先假定 skill 必定漏報，也不能沿用歷史綠燈宣稱有效。

「新專案本批變更前」版本仍可用來定位本批造成的回歸，但**業務是否正確的主要基準是約定的舊專案版本與核准例外**；新專案先前版本本身也可能已有錯誤，不能以新新一致取代新舊一致。

## Boundaries

- 本輪依使用者後續「執行任務」要求完成下列驗證；沒有修改 skill 或真實業務程式。
- 後續第一輪以隔離、循序、記憶體內 Java 情境驗證 skill。真實 DB／MQ／交易代理／並行／部署切換須另有適用證據，不外推模擬結果。
- 不改真實業務 repo、不安裝全域依賴、不清理未提交內容、不提交／推送來源 repo、不發布平台 review。未來 fixture 可在專用暫存 repo 建立固定本機 commit。
- 不要求本批搬完所有功能；未排入本批且非必要相依的功能只列待移轉，不當成本批缺陷或 Hold 理由。
- 本批承諾的功能若缺必要規則，或入口仍依賴未接通功能，不能用「之後會搬」解除本批問題。可接受的過渡行為須有契約與證據。
- 不自動保留／修復已知舊 bug。忠實移植的品質風險另列；修復若改變行為須有核准來源，結果不能稱嚴格等價。
- 不新增通用移轉平台、全 repo 圖分析器或三方 helper；先使用現有工具與簡單規則表。普通 PR 的規則不因本情境而全面改寫。

## Assumptions

- 架構調整預設不改業務語意；明確核准的例外按功能／規則記錄，不視為全面豁免。
- 基準角色使用 `L_k`＝本批約定舊版、`N_prev`＝新專案本批前、`N_k`＝本批候選版。首批若沒有前次功能，`N_prev` 不作虛構的業務對照。
- 若舊專案仍持續修正，逐批固定 `L_k`，辨識相對前批舊基準的改動；是否納入本批須依既定範圍或取得決策，不自行跟隨浮動 HEAD。
- 人工案例沿用 Java 是為重用既有執行方式，不限制 skill 支援的語言。實際工具可用性於 T1 查核。

## 每批審查方式

### 1. 定義本批與累積範圍

以業務操作建立簡單移轉台帳，最低欄位為：功能 ID、舊入口／規則來源、目標責任、本批是否承諾、必要相依、移轉狀態、證據版本與未解問題。

狀態至少能區分待移轉、部分移轉、已移轉待驗證、限定範圍已驗證。這是預計的驗收紀錄，不預先建立新管理系統。前批已驗證狀態須有有效證據；不能只靠名稱、作者聲明或工作進度。

整個舊專案的功能清單逐步盤點；本批只要求相關來源完整。全量清單尚未完整時可做局部審查，但不能宣稱整體移轉完成。

### 2. 舊側先盤點，再核對新架構

先從本批舊入口追 caller、guard、設定、SQL 與副作用，形成 Rule ID：輸入接受域、條件優先序、預設值、計算／精度、權限、狀態轉移、錯誤、寫入、事件、交易及重試。

再映射到新架構的實際責任，允許一拆多、多合一或跨層；舊→新找漏搬，新→舊找新增限制／副作用與核准依據。不能只讀新 diff、同名 class 或新測試。

### 3. 三類證據各自回答問題

| 比較 | 用途 | 判斷限制 |
|---|---|---|
| `L_k → N_k` 本批功能 | 規則與可觀察業務行為是否一致 | 主要驗收依據；架構相似不代表一致 |
| `L_k → N_k` 受本批影響的已移轉功能 | 前批功能是否仍符合舊業務基準 | 需考慮舊基準更新與核准例外 |
| `N_prev → N_k` 差異與回歸 | 定位本批改動、影響 caller 與證據失效範圍 | 輔助歸因；兩版都有錯也可能一致 |

對跨功能流程另以同一業務操作序列比較舊、新結果，例如建單→部分退款→重播。兩側初態須業務等價且獨立，控制時間、亂數、設定和外部回應；觀測回傳／錯誤、狀態、寫入、事件及操作順序。adapter 只能轉換表示，不能補規則或抹掉差異。

若過渡期間確實保留新→舊呼叫，才查路由、契約與失敗語意；不能假設存在 bridge，也不能因未來規劃有 bridge 就視為已接通。

### 4. 形成批次結論與累積狀態

- 未核准反例：該規則 FAIL；有效阻擋未解除則 Request changes，同時保留其他未知。
- 必要來源／執行／觀測缺失：相關規則 UNKNOWN；沒有已確認阻擋時為 Hold，列最小補證。
- 本批必要規則有適用證據、受影響已移轉功能未退化、必要相依成立：可給本批限定 PASS／Approve。
- 有核准行為差異：明示「符合約定契約，含例外」，不可稱嚴格等價。
- 未到本批的獨立功能仍為待移轉；本批 Approve 不等於整體移轉完成。

基準、契約、共用程式、資料映射、runner 或環境改變時重新核對受影響證據。沒有變動且證據仍適用的項目可沿用並說明理由，不要求每批無差別全量重跑。

## Skill 驗證情境

以同一個人工舊專案建立兩批演進：第一批搬建單／金額計算，第二批搬退款並重用新架構相依。舊版包含兩者，讓跨批流程有真實舊側對照。保留另一個不影響本批的待移轉功能，驗證 scope 判斷。

具體金額、門檻及狀態契約於 T2 固定。以下是 evaluator 的設計與預期，不能交給盲測 reviewer；所有候選版從正確版本獨立派生，不疊加缺陷。

| ID | 情境 | 預期及可驗收重點 |
|---|---|---|
| C0 正確分批改架構 | 舊方法拆成 service／policy／repository；兩批規則一致，無關功能留待後批 | 本批 Approve；不得因不同 class／層次或無關待移轉功能誤擋；整體狀態仍未完成 |
| C1 本批規則漏搬 | 第二批退款漏掉一個舊側合法邊界或拒絕 guard | Request changes；由舊規則找出可達反例，不依賴新測試刻意提示 |
| C2 副作用不一致 | 回傳金額正確，但退款拒絕前已修改訂單狀態，或重播再次發布事件；T2 選定一個根因 | Request changes；定位順序／責任與實際副作用差異，不能只比較回傳值 |
| C3 先前批次回歸 | 第二批抽取共用計算時改壞第一批建單邊界，本批退款仍正確 | Request changes；追未改動 caller，對回舊建單規則及前後差異，不能只驗本批退款 |
| C4 必要相依未移轉 | 第二批承諾退款但新入口接到未實作的必要庫存回補責任；無核准替代流程 | 有可達違約反例則 Request changes；與 C0 的無關待移轉功能區分，不能把必要缺口排到範圍外 |
| C5 必要證據缺失 | 正確來源，但一條必要拒絕／重播路徑無可取得的舊側觀測，且沒有足夠替代證據 | 該規則 UNKNOWN、總體 Hold；其餘已驗項保留，不捏造程式 bug 或全域 PASS |

C5 須在 reader 內確保缺口真實存在，不能只刪 logs 卻允許重跑取得相同證據；可提供受限來源／受控外部依賴，並明示執行限制。若實際能補證，應允許 reviewer 補證，不強迫 Hold。

驗證案例至少涵蓋：正常、門檻前／等值／後、拒絕、失敗、重播及建單→退款序列；精確案例數由契約決定。每項負例必須有能區分正確／錯誤版本的觀測。額外維護情境如舊基準變動先納入指引稽核，有失敗證據再增測，不擴成無限矩陣。
