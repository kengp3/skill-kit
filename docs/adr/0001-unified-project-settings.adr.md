# 由 project-setting 統一管理專案設定

日期：2026-10-25。狀態：本輪設定整合、模型主導流程、模型分工、最低驗收及交付範圍的決策已記錄，待整體定稿確認；具體實作與宿主能力仍待驗證，尚未實作。

本輪範圍包含三項必要調整：整合 project-setting 與 task-harness 的設定方式；去除 task-harness 對 runtime script 的必要依賴，腳本改為選配，以 hooks 觸發流程要求並內建不可用時的接手流程；允許依任務階段、任務及 agent 分別設定使用模型。三項調整須一併交付。

project-setting 保留單獨管理文件規範的能力；使用者指定「包含 task-harness」，或明確執行 task-harness 後由其委派設定時，才一併設定其區段與對應 hooks。單獨使用 project-setting 不新增 task-harness 的 hooks 需求；個別任務仍需明確啟用 task-harness。

task-harness 核心不得依賴任何 runtime script；所有此類腳本皆為選配輔助，不只限於 Python，也不只是在使用者機器省去 runtime 安裝步驟。不得以更換語言或內附 runtime 的方式，保留腳本作為使用前提。解除必要腳本依賴列為本輪必要修正，與設定整合一併討論及交付，不延後為可選改善；此要求取代先前把缺少 Python 視為必要接入缺口的設計。

task-harness 主要使用模型能力完成設定判讀、任務拆解、模型分工決策、進度核對與驗收判斷；任何外部工具、CLI、MCP 服務或 runtime script 均不得成為核心使用前提。選配工具可以提供輔助證據或自動化，但缺少時不能阻擋 task-harness 使用，也不能以外部 dispatcher 或 validator 取代原本的必要腳本依賴。這是 harness 本身的依賴限制；個別任務所需的實際操作或測試，仍須如實記錄執行證據，不能以模型判斷宣稱未執行的測試已通過。

使用者指定以 hooks 的強制力作為不依賴 runtime script 的方向；hooks 仍屬標準接入流程，負責在關鍵生命週期觸發流程要求，內容判讀與後續行動主要由模型完成。宿主事件觸發、指令注入、條件式阻擋及續作是不同能力，須依實際支援與證據界定；不能把固定提醒宣稱為已機械檢查合約，也不能將原 Python handler 的條件判斷或原子收據保證直接視為仍然存在。無外部工具依賴的具體 hook 接線與控制能力仍待驗證，不預設先前提出的系統命令接線已獲同意。

hooks 缺失、失效或宿主不支援時，task-harness 先在原授權內診斷並嘗試修復，設定操作交由 project-setting；修復後仍無法使用時，由 task-harness 內建流程自動接手，讓模型主動完成流程檢查並繼續整個任務。不因 hooks 不可用就退出 task-harness、暫停整個流程或要求使用者另行同意一般協作模式。此決策取代先前將 hooks 可用性視為使用前提的設計；任務合約、授權與驗收要求持續有效，接手不能繞過使用者停止指示或實際任務阻礙。須如實記錄 hooks 狀態與接手方式，不將模型主動檢查宣稱為宿主強制攔截，也不虛構 hook 事件或技術收據。

hooks 觸發與模型主動檢查共用同一套檢查規則及同一份任務合約，不另維護接手模式的規則或任務狀態。hooks 不可用時，由主責模型在以下時點主動檢查：開始或恢復任務時，確認設定、授權、進度及下一步；派工或切換階段前，確認前置條件、負責 agent 與模型；agent 回報後，核對成果與證據並更新任務狀態；準備結束前，逐項核對完成條件，仍有可執行的必要工作就繼續。觸發方式改變不降低原定驗收要求。

確認 hooks 已實際恢復後，自動依同一份任務合約及現有執行證據銜接目前進度，不重啟任務或另行詢問。恢復或重複觸發本身不是重做操作、重新派工或重新驗證的理由；已完成的操作不重做，已啟動的 agent 不重派。狀態不明時先查明再行動，成果或條件改變時才重新驗證相關項目。

現有 Python helper 與開發端封裝、測試工具須與日常使用需求分開；可選 helper 缺失不得間接阻擋任務驗證或 review。開發端仍可使用 Python，使用者日常流程不要求先執行 Python 建包。核心驗收須涵蓋所有選配腳本不可用的情況，不能用腳本可用時的成功代替。此記錄未宣稱現行接入已符合新要求。

task-harness 負責提供自身的設定方式、Markdown 格式、欄位定義、範本、有效性規則、移轉及修復規則與所需驗證方式。project-setting 負責依提供的規格執行設定操作、保留無關內容、檢查寫入邊界並讀回核對；其本體不內建 task-harness 專用欄位、預設值、移轉或業務驗證邏輯。共用設定檔不轉移各技能對設定內容的責任，也不讓 project-setting 依賴 task-harness 才能使用。

task-harness 隨技能附帶並維護 Markdown 設定規格文件，包含欄位、預設值、表格範本、驗證及移轉規則。指定包含 task-harness 或由其委派設定時，將該規格提供給 project-setting，由模型讀取並依規格執行設定。project-setting 僅保留通用的「依指定規格設定」流程，不內建 task-harness 專屬邏輯，也不需要額外註冊服務或執行腳本。規格文件描述設定規則；專案實際設定仍以 project-setting.md 為唯一來源。

模型分工須允許不同任務階段、任務或 agent 使用不同模型，不能只設一個模型套用所有工作。專案長期模型設定統一使用 project-setting.md，沿用同一責任分工，由 task-harness 提供規格，project-setting 執行設定操作。

單次任務指定的模型、推理強度與替代安排只記錄於該任務合約，恢復同一任務時仍有效，新任務不自動沿用。只有使用者明確要求設為專案預設時，才由 project-setting 更新 project-setting.md；不將本次指定自動寫成長期設定。任務合約記錄本次覆寫及實際使用結果，不複製整份專案設定，也不成為第二份專案設定來源。

模型分工提供規劃、執行、驗證、審查四個預設階段，並允許專案自訂階段。規劃涵蓋需求釐清、方案研究及任務拆解；執行產出任務成果；驗證執行檢查並核對成果與驗收證據；審查評估品質、風險與遺漏。各階段可分別設定模型、推理強度及替代模型，不預先綁定特定模型。階段名稱供模型設定對應使用，不強制每個任務走完所有階段；未設定時沿用已確認的模型選擇優先序與預設行為。

主責 agent 使用使用者在對話中選定的模型，負責任務合約與協調；task-harness 不會因階段設定自行切換主責模型。需要不同模型的各階段或任務，交由指定模型的 agent 執行；個別任務可指定模型，不要求每個小步驟都建立 agent。

宿主無法建立子 agent 時，先在原授權內診斷並嘗試修復；仍無法派工時，由主責模型依原任務分工循序接手，沿用同一份任務合約與檢查規則，記錄實際執行者與模型，不引入外部派工工具。這與指定模型不可用時依替代清單選擇模型的情況分開處理，也不代表主責模型已切換成原先指定的模型。若任務明確要求獨立 agent 審查，主責自我檢查不能滿足該條件；該驗收條件保留未完成並回報，其他工作繼續。

使用者於任務途中手動切換對話模型時，後續依規則沿用主責模型的派工跟隨最新選擇；已啟動的 agent 維持原模型及推理設定，不自動重啟或改派。這不覆蓋仍有效的任務、角色、階段或專案模型設定。介面選擇對話模型與明確要求所有 agent 使用某模型是不同範圍的指示。

模型選擇優先序由高至低為：本次使用者明確指定、個別任務設定、agent 角色設定、任務階段設定、專案預設模型。皆未設定時沿用主責模型。這是 task-harness 的選擇規則，仍須核對宿主實際採用結果；模型已指定但不可用的情況不等同未設定。

指定模型不可用時，依預先設定的替代模型清單依序嘗試，回報替換原因與實際使用模型。替代清單支援最後一項 default，但回退預設模型本身是預設行為，使用者不必手動加入：首選與替代清單均不可用後，有專案預設模型就使用專案預設，沒有專案預設才沿用主責模型。同一次模型選擇與替代流程不重複嘗試相同模型。這取代先前「必須加入 default 才允許回退」的建議。

包含預設回退在內仍無可用模型時，暫停該項工作並詢問，其他不受影響的工作繼續。啟動結果不明或逾時時，先核對 agent 是否已執行，避免重複派工。

模型優先序用於決定首選，替代模型清單另行管理；除已確認的末段預設回退外，不將較低優先序的角色或階段設定自動當成替代鏈。

同一設定對象的模型嘗試順序以有序清單表示，例如 `[模型A, 模型B]`：第一項為首選，其餘項目依清單順序替代。不採每個候選模型各占一列並另填嘗試順序編號的提案。清單順序具有語意，與 Markdown 表格允許調整列順序的規則不同；末段預設回退仍自動處理，不要求列入 default。候選模型與其推理強度以分號連接，候選項目以逗號分隔，例如 `[模型A;high, 模型B;medium]`；不使用括號附註強度的提案。不指定強度時可省略分號與強度，例如 `[模型A;high, 模型B]`，模型B 使用宿主對該模型的預設強度。範例只定義表示方式，不代表選定實際模型或保證各宿主支援範例強度。

首選與每個替代模型皆可各自設定 reasoning effort。明確指定模型但未填推理強度時，使用宿主對該模型的預設；完全沿用主責時，一併沿用主責當前的模型與推理強度。替換模型時採用該替代項自己的推理設定，不將原模型的強度直接套用到另一模型。目前沒有選定具體模型、強度或預設映射，也未變更宿主模型設定。

模型可用但宿主不支援指定推理強度時，優先保留該模型，使用宿主對該模型的預設強度並記錄原因；仍無法啟動時才依既定替代清單繼續。使用者明確要求強度不可變更時，遵守其限制，不自行改用預設強度。此調整屬本次執行結果，不代表已修改專案設定或原始任務指定。

task-harness 設定統一納入 project-setting.md，沿用其 Markdown 格式；不另維護 harness-project.json，也不在 Markdown 內嵌另一份 JSON 設定。文件位置與 task-harness 使用同一份專案設定，避免兩套設定需要人工同步。

包含 task-harness 時，在現有「類型／文件用途／目的地與檔名」分類表新增 task-contract 與 hook-receipt，分別管理任務合約及 hook 技術收據的位置。這兩列是唯一路徑來源，不另維護 contract_dir、receipt_dir。既有 plan、research 等分類保留；移轉沿用既有位置，不搬移合約或技術收據。

task-harness 依自身定義的固定 Markdown 表格讀取設定：文件位置取自共用分類表，其餘設定集中在 Task Harness 區段的「設定項目／值」表格。允許調整列順序及空白；必要欄位缺漏、重複或值無效時回報，交由 project-setting 按 task-harness 提供的規則處理，不自行猜測。一般說明文字可調整，識別用的區段、欄位名稱與格式由 task-harness 明確定義。先前由 hooks 自行解析表格的構想須配合核心不依賴 runtime script 的要求調整；選配解析腳本可重用相同格式，不得成為必要讀取途徑。

既有 harness-project.json 採一次性移轉：先提示將進行移轉，由 task-harness 提供移轉規則，project-setting 依規則嘗試讀取、合併進 Markdown，成功寫入並通過所需驗證後刪除舊 JSON，不另保留備份，也不長期維護兩套有效設定。此處依使用者後續指示，取代先前「成功後保留舊檔備份」的決定。移轉失敗或新舊內容衝突時，保留原檔並回報，不自行選擇或覆寫；不能因只存在舊 JSON 而默默停用。刪除範圍僅限已成功移轉的舊設定檔，不包含既有合約、技術收據或其他產物。

刪除舊設定檔須同時通過三項門檻：新設定成功寫入且與舊設定對帳無遺漏；通過 task-harness 提供的格式及內容驗證；確認目標執行版本支援新格式，且能依其正常使用流程成功讀回。讀回與驗證主要由模型依 task-harness 規格執行，不要求額外安裝解析器或驗證工具；仍須實際讀取新檔，不能只檢查預計寫入的內容。宿主信任與環境資格另外檢查並回報，設定移轉成功不代表它們已通過，也不將它們當成格式移轉完成的額外門檻。

舊設定的環境資格僅作歷史紀錄，移轉時記錄舊值及其處理結果，不直接將舊的「已通過」狀態沿用為新流程已驗證。新流程的可用性依本次實際診斷判定；hooks 無法使用時，依模型接手流程繼續。此處不增加刪除舊設定檔的門檻，環境診斷結果仍與設定移轉驗收分別回報。

執行 task-harness 時先檢查專案設定；設定缺失、仍為舊格式或有問題時，使用 project-setting 進行初始化、移轉或修復，核對通過後再繼續相依的任務操作。這些設定變更由 agent 透過 project-setting 完成，hooks 不自行改寫設定。衝突或需要使用者決定的內容先回報；原任務若限制唯讀或禁止設定變更，仍遵守該限制。

設定完成後，由 task-harness 在原授權內主動診斷並嘗試修復環境問題；設定操作仍交由 project-setting，完成後再由 task-harness 檢查。需人工操作或超出原授權時回報所需行動，僅暫停確實無法在現有授權與能力下完成的操作；hooks 問題按上述內建流程接手，不因此阻擋整個任務。不因可選 runtime 缺失要求人工安裝或停止使用，也不以修改資格欄位代替驗證。

本輪交付同步更新 project-setting、task-harness 技能本體及受影響規格、既有 Codex plugin 封裝，以及專案本地安裝／升級指南。封裝須同步新設定與 hooks 接入方式，指南涵蓋首次設定、舊設定移轉、模型分工及失效接手。在隔離測試專案驗收全新安裝與舊版升級，不修改其他既有專案或全域安裝。

本輪最低驗收範圍包含以下情境，須具備實際 agent 執行與產物證據；未驗證項目如實標示，不以文件描述或模擬結果宣稱實際流程已通過。

| 情境 | 必須確認的結果 |
| --- | --- |
| project-setting 單獨使用 | 不需要 task-harness，也不新增其設定 |
| 包含 task-harness | 能初始化、修復設定，保留其他內容 |
| 舊設定移轉 | 成功驗證才刪除舊檔；衝突或失敗保留原檔，既有產物位置不變 |
| 停用選配腳本與外部輔助工具 | 核心流程仍可執行 |
| hooks 失效及恢復 | 模型接手、恢復後銜接，不重複操作或派工 |
| 模型分工與回退 | 優先序、清單、推理強度及任務設定有效範圍符合約定 |
| 無法建立子 agent | 主責接手；獨立審查條件如實保留未完成 |

目前 runtime 仍讀取 harness-project.json，必要 hooks 仍直接執行 Python handler；本決策記錄不代表整合或解除 Python 依賴已完成。具體欄位、讀取細節及 hooks 實作調整仍待具體化與驗證。宿主載入與信任、執行環境資格，以及個別任務授權，不能由設定檔存在推定；設定初始化或修復也不能自行宣告環境資格已通過。
