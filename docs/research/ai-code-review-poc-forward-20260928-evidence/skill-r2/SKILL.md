# AI 程式碼審查

讓讀者知道結果、所有尚存事項、現在該做什麼，以及如何驗證解除。審查新增功能、缺陷修正、重構及移轉；移轉只是其中一種模式。不以 diff 大小、AI 信心、格式完整或測試全綠代替判斷。

## 流程與階段產物

依序完成：**① Git diff 目標清單 → ② 全目標關聯與影響分析 → ③ 深度審查 → ④ 最終報告**。前兩階段是審查輸入，不以變更摘要代替第三階段。各階段產物可保留在同一份工作紀錄，不必建立四份文件。

## ① 固定來源並盤點所有目標

開始時記錄實際執行時間及時區。取得目標 repo、base/head 或工作樹範圍、需求／規格及適用專案規則。先讀來源與狀態，不切換／清理使用者工作樹。ref 解析成完整 commit 並保留原 branch 名；跨 repo 不猜共同祖先。

- 一般 PR／分支：核對 merge-base，以固定 commit 的 `git diff <base>...<head>` 定位改動，同時讀完整方法、caller、guard、配置及相關測試。若使用者要求比較兩個精確版本的內容，採雙點／直接快照比較並明示，不偷換成 merge-base。
- 工作樹：區分 staged、unstaged、untracked，固定納入的檔案內容與 hash；不假稱全部屬 HEAD。未要求的 untracked 不自動納入。
- 只給 class：作為搜尋起點，追蹤責任、消費者與必要副作用，明示局部範圍，不宣稱全 repo 已審。
- 缺 ref 或需求：先查可用材料；會實質改變結論且無法安全推論時才詢問。可進行的品質查核繼續；缺正式 spec 不自動阻擋所有 review，只有影響必要判斷的缺口列 UNKNOWN。

記錄實際採用技能、reference、規則與工具之路徑／hash；未知模型版本不猜測。固定快照及結構化差異需要時讀 [evidence.md](references/evidence.md)，使用 `scripts/review.py`。它僅支援 committed snapshot，不執行業務程式，也不是通用缺陷偵測器；工作樹改用內容快照，明示邊界。

先取得完整檔案狀態及 patch，建立目標清單：固定版本、檔案舊／新路徑、增改刪／改名、差異區塊、檔案用途與分析狀態。非程式、測試、配置、生成及二進位檔亦列入；生成檔可對照生成來源／工具，不假稱已逐行審查。輸出清單及比較語意後才進入關聯分析。

## ② 分析所有目標、關聯與影響

將變更對應到 class／方法、簽名、欄位及初始化等責任，相依來源與 diff 分開。無法讀取／截斷內容須列缺口；跨 repo 無共同歷史時明示來源對照，不虛構 PR diff。

逐一分析清單中的所有檔案及差異區塊，讀完整受影響方法／責任與必要上下文；測試、配置及文件用其實際責任分析。每項記錄「目的 → 前後行為 → 關聯入口／消費者 → 資料與副作用 → 影響範圍及不確定邊界」。需求或作者說法與原碼實際作用分開。遇大範圍可分組，但不能漏掉待查項。

依分析結果判斷需要哪些圖，使用 [report.md 的選圖規則](references/report.md#圖表說明關係與證據邊界)：類別、流程／活動、循序、狀態或其他適合的 UML／關係圖皆可。先確定需解釋的結構、分支、互動順序或狀態，再選能支援判斷的最少圖組，不固定每次必畫類別圖加流程圖。說明選圖理由；多圖各自回答不同問題，不用單純 class 條列代替關聯。圖須能回到固定來源、保留重要 guard／錯誤路徑，來源不足即標缺口。此階段產物是全目標分析、變更摘要、選圖理由、圖與影響邊界。

## ③ 深度 code review

讀 [deep-review.md](references/deep-review.md) 並執行其步驟。先整理需求與不變條件，再沿完整業務／程式路徑查正確性、安全、可靠性、效能、設計及相容性；核對候選問題的可達性與反證，驗證測試是否真能捕捉錯誤，最後對帳所有目標。產物是具證據的問題／缺口清單及查核完成狀態，不是泛用建議清單。

### 按變更目的判斷

先從需求建立必要行為與風險，再讀舊實作及新實作、測試和呼叫關係。需求事實、推論與假設分開。

| 情境 | 判斷依據 |
|---|---|
| 新增／變更功能 | 以核准需求檢查新行為；有意且符合需求的舊新差異不是回歸 |
| 缺陷修正 | 舊觸發案例在新版正確，並檢查相鄰邊界及未授權副作用；原 bug 不應被要求保留 |
| 重構 | 約定外部行為保留，允許結構改變；有必要時用相同案例比較 |
| 新舊系統移轉 | 讀 [migration.md](references/migration.md)，舊規則先行、多對多映射、雙向盤點及必要執行證據；不要求同名 class |

不對所有 PR 強制套用「新舊必須一致」。多種目的並存時按業務責任分組，分清哪些可改、哪些應保留。原規格與新需求衝突時記錄來源及缺口，不選最容易通過的版本。

### 查核與證據

1. 檢查正確性、安全、可靠性／效能、設計／可讀性、測試及相容性；依語言、框架與實際風險取捨，記已查／不適用／待查，不填制式改善清單。
2. 沿 caller 與資料流核對觸發可達性、guard、錯誤／交易／事件等責任。對候選問題主動找反證；原有問題與本次新增／加劇分開，偏好不自動阻擋。
3. 有執行授權時重用最小相關測試，補必要正常、邊界、拒絕、失敗案例；保留實際命令、退出碼及原始輸出。只讀測試不是執行，建置成功不是功能正確，模擬 side effect 不證明真實提交。
4. 比對測試是否覆蓋約定需求；有限案例不保證所有輸入正確。已確認來源缺陷可直接形成 finding，不強迫每個問題都有重現；猜測列調查項。缺執行證據不能捏造成程式缺陷。
5. 重審沿用穩定 ID，固定新版本並核對修正與受影響證據，才標 verified。沒重驗的修復為 fixed-pending-verification；不因作者說修好或換 hash 自動結案。

只在確有風險時擴大查核，避免無限補測。流程完成可得到 FAIL 或 UNKNOWN，不為取得 PASS 修改被審程式或縮小約定範圍。

## ④ 完成審查後交付報告

完成第三階段及範圍對帳後，依 [report.md](references/report.md) 的五章順序產生最終報告：**基本說明 → 範圍說明 → 關聯與流程 → 審查結果與問題 → 結論**；證據附錄在後，**完整檔案清單為最後一節**。首頁列執行日期時間、專案完整路徑、目的摘要與簡短通過／不通過／暫緩結論。問題正文優先呈現可定位的原始短碼及建議修改碼／註解，再補原因、影響及解除條件。無法可靠給碼才說明理由及具體下一步。

必要步驟未完成時，可以交付明示「部分完成」的報告，保留已確認問題與所有必要缺口；不能提前宣稱完整審查或 Approve。

分開審查執行狀態、需求符合性／品質、必要時的行為一致性：

- 有已確認且未解除的阻擋：Request changes（要求修改），保留其他缺口。
- 無已確認阻擋，但約定的必要證據欠缺或未完成：Hold（暫緩），寫最小補證方式。
- 約定範圍已完成、必要證據有效且無未解除阻擋：Approve（建議通過），不宣稱全域正確。

阻擋需連到需求、適用政策或具體風險，不能用嚴重度或信心自動決定。無真實 PR 時給範圍結論，演練建議明示；Hold 是報告用語，不是平台動作。報告不代表已提交 review 或已禁止合併。

每次產出後，實際閱讀報告並按 report.md 核對：開頭能否回答結果、全部待辦與第一步？正文位置、原因、建議與解除條件是否對上證據？不足先修報告；技能改善在授權內以具體失敗為依據，改後重新套用情境驗證，不累積未經驗證的通則。

本技能不授權修改被審程式、全域安裝、提交、推送、平台評論或部署；依本次已給授權執行，不重複索取許可。
