# 移轉業務一致性審查

比較的是業務規則與可觀察行為，允許新舊類別、方法、資料表及語言不同。不以文字相似度、測試全綠或 AI 信心宣稱普遍等價。交付可追溯的規則證據及獨立的一般品質結論。

## 固定範圍與版本

開始本輪時記錄實際執行時間及時區，供報告基本資訊使用；無紀錄不事後猜測。取得舊 repo/ref、新 repo/ref、業務操作（或 class 作搜尋起點），讀取兩側適用指令與現有測試。兩個 repo 不需要共同歷史。明示 scope 優先；若只給 class，查閱 caller 與相依來辨識相關規則和副作用，但不擅自擴大驗收範圍。資料不足先做可進行的來源審查，必要缺口列 UNKNOWN。

先寫出驗收邊界：比較公開 API 的完整輸入域，或特定入口及其可達業務情境；列保留的輸入、狀態與副作用。只有 class 而未指定契約時，可先做局部 API 比較，但須標為比較假設，不把局部差異直接升格為整個移轉 PR 的阻擋。

優先使用 Git 完整 commit；開始時記下 branch 解析結果。使用者要求工作樹時，另保存所有納入檔案的內容及雜湊，不混稱 committed snapshot。本技能 helper 僅支援已提交版本，排除 dirty／untracked，必須明示。不得切換或清理使用者工作樹。

載入時記錄實際採用的 SKILL.md、reference、專案規則與執行工具之路徑及版本／內容 hash，隨本輪證據保存；未讀或未採用的不列為生效規則。無法取得的模型標籤或版本明示未知，不猜測。重審分開核對原始執行證據與審查判斷是否仍適用，細節見 report.md。

需要固定快照或比較結構化觀測時，讀 [evidence.md](evidence.md)，使用本技能 `scripts/review.py`；從實際技能目錄定位腳本，不假定目前工作目錄。若整包快照會讀到範圍外或禁止存取的內容，改用定向 `git show <commit>:<path>` 保存選定來源、相依清單與 hash；明示此為範圍快照，不宣稱全 repo 完整。純來源 review 不要求 Python。Git diff 可協助定位同 repo 的改動，但不能取代完整舊規則盤點；跨 repo 不猜 merge base。

## 舊側先行，再雙向對照

依業務操作把相關新舊來源一起審查；共用相依可被多組引用，但保留一份範圍清單，逐項記錄已查、待查或排除理由。分批、上下文不足或工具失敗不能讓項目無聲消失。只套用符合實際語言、框架與部署方式的品質檢查；必要規則不因沒有 diff 或檔名改變而略過。

先辨識每組的契約變更風險，列最小查證動作及其要回答的問題，再讀取相關來源或執行案例；風險假設不是 finding。刪除的 guard、規則與副作用也須追蹤替代位置，不照搬只審新增程式碼的限制。

1. 先獨立盤點舊側的輸入限制、條件優先序、預設值、計算、權限、狀態、外部命令、錯誤、交易與重試。每條建立 Rule ID、side/commit/path/line 及最小來源摘錄；實際程式與文件矛盾時記錄矛盾，不把註解當答案。
2. 追蹤相關常數、設定、SQL、trigger、排程與序列化。無法取得的必要來源列未知。以另一類來源（既有測試、配置、執行結果或確認的規格）交叉核對高風險規則。讀過測試只是來源證據，必須實際執行才算 tested。
3. 舊→新逐條建立多對多映射；新→舊查新增 guard、預設值、事件與寫入。名稱匹配只作定位線索。移除規則須有明確決策來源，不可自行判定不再需要。README 記載有意改變可證明設計意圖，但不自動等於使用者核准移轉例外；有意差異也不一律是 coding bug。
4. 查閱實際 caller，確認哪些內部狀態會成為回應、資料或授權判斷。Java 特別注意代理／交易邊界、例外包裝、非同步脈絡、精度、時區及 JSON 缺值。按實際版本／配置判斷，無圖不代表不追呼叫者。

## 可執行證據

有執行授權時優先重用專案測試，必要時新增最小 harness（測試驅動程式）。兩側以同一業務案例、等價且獨立初始狀態、受控時鐘／亂數／設定／外部回應執行；相依或 JDK 衝突則分程序。只有來源 review 授權時不擅自執行。

- 比較回傳／錯誤、實際持久化狀態、事件及對外請求、rollback、重試／冪等與必要操作序列。mock 呼叫不證明真實提交或 rollback。沒觀測到的項目不能填空值冒充「沒有副作用」。
- 按規則建立正常、邊界、拒絕、失敗與序列案例；並行或切換語意需要對應環境證據，單次 sequential 測試不能代替。
- 保留原始輸出。adapter（結構轉接程式）只改表示，不實作／補齊業務規則；資料映射獨立驗證。ID 映射須一致且一對一，保留資料關係、重複數與有語意的順序。金額、權限、狀態、有效期與錯誤不能任意忽略。
- 先 old→old 校準，再用已知錯誤（改門檻、重複事件、錯關聯等）確認比較器會抓錯。不能以新輸出自動更新舊基準。版本、契約、adapter 或輸入變更後重驗受影響證據。
- 不能執行舊側或缺必要觀測時，交付來源 finding 與具體補證案例，維持 UNKNOWN。圖分析及形式工具皆非必要依賴；外部工具的 Maybe／timeout／bounded 結果不是完整證明。

## 一般程式品質審查

另查正確性、安全、效能／可靠性、設計／可讀性、測試、相容／運維。每類記錄已檢範圍、證據或不適用原因；只報有具體觸發與影響的 finding，不填制式建議。一般 finding 要有 severity、精確位置、觸發條件、影響與最小建議。

沿用舊漏洞可能業務一致但品質不合格；修正舊漏洞也不能未經決策就稱為等價。區分原有問題、新回歸、核准例外與比較環境問題。

## 判定與交付

候選 finding 出報告前，回查完整方法、caller、guard、設定及版本，主動找能推翻主張的證據。已證實不成立才標 false-positive 並記理由；無法確認則保留為調查項，影響必要規則時列 UNKNOWN，不因低信心刪掉，也不升格為已確認缺陷。定位錯誤先修正引用，不因此丟棄有效問題；移轉證據可位於 diff 外。這是來源與證據查核，不是再問一次 AI 是否同意。

反證查核逾時、來源不可讀或工具失敗時，保留候選及失敗原因、未解前提與補證方式。已有有效反例不因查核失敗而消失；僅有猜測則不得升格為已確認缺陷或標成誤報。必要查核未完成須反映在執行狀態及缺口中。

確認觸發輸入在約定邊界內可達。上游已驗證的防護若排除反例，收斂影響與阻擋判斷；直接方法測試仍可證明 API 差異，但不證明入口故障。反之，不可只因新增 guard 拒絕了舊側合法輸入便消除差異，須比較同一入口的接受域及錯誤語意。

每條規則獨立標示證據種類（source-reviewed／tested／formally-proven-with-assumptions）及 PASS／FAIL／UNKNOWN。helper 的 PASS 只代表其列明觀測一致，不能直接抄為移轉 PASS。

- **FAIL**：有有效的未核准反例；其他未知不能抹去已確認差異。
- **UNKNOWN**：必要來源、案例、觀測、執行或映射證據欠缺／失效。來源看起來一致不能單獨 PASS。
- **PASS**：指定範圍內所有必要規則有適用執行證據或經查核的完整形式證明，雙向盤點與必要副作用／序列完整，無未核准差異及未知。這是限定範圍驗收，不保證未測輸入或未發現規則。

核准例外記錄誰、何處、哪條規則及允許的差異；結果稱「符合契約，含例外」，不可稱嚴格等價。審查可結案為 FAIL／UNKNOWN，不需為得到 PASS 而修碼或縮小原定範圍。

產出或重審報告時，讀 [report.md](report.md)，依其五章順序交付，完整檔案清單置於最末端。關聯與流程依分析結果選擇適合的 UML／關係圖，說明選圖理由，區分來源推導與實跑證據；新舊規則映射不能畫成兩系統互相呼叫。產出後按 report.md 的讀者核對檢驗實際報告，修正遺漏或矛盾再交付。分列審查執行狀態、業務一致性與一般品質結論；有 PR 時另給合併建議，不將流程完成或 helper 結果直接映射為核准。

合併建議依序判斷：有有效且未解除的阻擋問題為 **Request changes**；否則必要證據缺漏、過期或約定審查未完成為 **Hold**；其餘才建議 **Approve**。阻擋須連到約定契約、團隊政策或具體風險，不以嚴重度、個人偏好或 AI 信心自動決定。Hold 是報告內的暫緩狀態，不是平台原生動作；報告、平台已提交動作及實際合併條件分開標示。

交付依目標專案文件規範。技能不授權提交、推送、發佈評論、安裝分析器、正式環境重播或移轉切換；按本次任務已給的授權執行，不重複要求核准。
