# 深度審查：從需求到可驗證問題

在 SKILL.md 第三階段使用。輸入為完整差異目標、關聯圖及影響分析；不以圖表完成或工具綠燈取代審查。

## 1. 建立判斷基準

按業務責任整理必要行為與不變條件：入口／前置狀態、有效輸入、預期輸出與副作用、禁止的效果、來源。區分規格事實、作者意圖及推論。檢查測試的斷言是否符合需求，不把當前實作或新測試自動當需求。

功能變更容許核准的行為差異；修復不保留原 bug；重構／移轉才核對約定的行為保留。缺正式規格不代表完全不能審查：先查可確認的 API、規則與風險，只有必要且無法確定的判斷列 U 缺口。

## 2. 沿關聯查路徑，按風險增加深度

每個目標皆分析，相關檢查採下表。保留「查核面向／範圍 → 方法與證據 → 結果或缺口」紀錄；不適用要有範圍理由，不能只把矩陣全打勾。

| 面向 | 具體查法 |
|---|---|
| 功能與業務正確性 | 從真實入口追輸入、guard、轉換、狀態更新與結果；檢查正常、空值／邊界、拒絕、例外路徑。金額、數量、日期依實際型別與契約檢查精度／溢位／時區。 |
| 安全與信任邊界 | 追不可信輸入到敏感操作，確認驗證、身分／租戶／資源授權、注入與敏感資料輸出；上游防護需能證明存在且不可繞過。依賴有變更才核對相關供應鏈風險，不憑版本號宣稱無漏洞。 |
| 可靠性與副作用 | 對狀態更新、資料提交及外部呼叫逐點問「此處失敗／timeout 後留下什麼」；查回滾、補償、重試、冪等、資源關閉與取消。模擬呼叫成功不證明真實交易提交。 |
| 並行與順序 | 有共享狀態／非同步時列具體交錯：讀取 → 檢查 → 更新 → 發布；查 atomicity、可見性、鎖順序、回呼／重入及等候者如何解除。測試綠燈不窮盡排程。 |
| 效能與資源 | 以實際輸入量／熱路徑查新增查詢、N+1、無界迴圈／集合、阻塞與資源持有；有具體風險才量測，不憑想像報效能缺陷。 |
| 設計、維護與相容性 | 查責任與依賴方向、重複邏輯、過度抽象、API／序列化／資料庫／配置契約及消費者。風格偏好標非阻擋；文件與測試也檢查是否隨行為更新。 |

Java 情境若相關，另查多載、動態 dispatch、null／Optional、equals/hashCode、checked／unchecked 例外、executor／interrupt、交易 proxy 與 serializer 設定。其他語言套用其語意；不要求安裝專用分析器。反射、DI 或動態關係未能確認時標不確定，不捏造完整 call graph。

## 3. 對每個候選問題找反證

沿「觸發條件 → 可達入口 → 責任點 → 可觀測錯誤 → 違反規則」形成因果鏈。主動查 caller、guard、配置、契約是否排除案例；排除就撤回／修正 finding。區分本次新增、加劇與既有問題，明示實際影響及阻擋理由。同根因多個症狀合併，保留所有受影響位置與案例。

確定的來源缺陷可列 finding，不強迫每項都有可執行重現；未確認前提列調查或 U，不當成已證實 bug。既有有效阻擋與未知必須並存，不因找到一個問題就停止全目標審查。

## 4. 驗證實作，也驗證測試與建議

有執行授權時重用最小相關檢查。確認測試的輸入／斷言有涵蓋需求，而非只重述實作；必要時以已知壞版本／受控改動做紅綠對照，隔離執行並明示人工情境。保存實際指令、版本、退出碼、原始輸出與觀測，不只記「pass」。無執行條件時明示來源推導與未完成必要觀測。

建議修法優先給最小可定位程式碼／diff 與註解，查其 API 真實存在、guard／清理仍保留、是否影響同根因的其他 caller。只有實際套用並跑相關檢查才稱已驗證；示意碼／參考實作須標示，未知 API 不編造。

## 5. 審查結束門檻

逐一對帳目標：所有差異區塊是否理解、所有適用面向是否查核、所有必要缺口是否留下具體補證、所有 finding 是否有位置／原因／建議／解除條件。記錄已查但無問題的領域，避免把「沒報 finding」誤當未審。

必要項未完成不得說完整審查；已完成且存在阻擋仍可 Request changes。判斷規則與五章報告依 report.md。用讀者角度回讀實際報告，不能只驗證標題有出現。
