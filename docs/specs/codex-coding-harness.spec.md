## Problem Statement

### Objective

以整個 simple-skills repo 作為個人 harness 的開發、整合與維護單位，首版完成最小但完整的 Codex coding harness，服務既有專案的 bug 修復、功能開發與重構。首要改善「需求理解錯誤造成返工」及「交付不可信而需人工查驗」。在維持交付品質的前提下，以減少總人工投入為主要目標、減少打斷為次要目標；不要求使用者計時、填表或持續觀察。機制只整理可取得的證據，人工時間缺值保留未知，不以自動事件指標替代人工省時證明。

### Background

本規格依據截至 2026-10-24 的研究、原 Q1–Q27 設計討論與首輪 smoke 後的 R01–R07 決策。後者取代舊的人工觀察要求及 Desktop 延後定位。評估對象是 coding harness 整體：模型所在的宿主、專案環境、工具、工作流程、狀態與驗證回饋，不限於一份 skill。

[既有研究](../research/coding-harness-best-practices-20261024.research.md)提供來源與歷史比較；其中「先保留既有框架」的建議，已被本次決策取代。變更前 task-harness 及完整依賴的固定快照是 B 組比較基準；[目前來源](../../skills/task-harness/SKILL.md) 屬候選演進來源，不構成新版必須沿用的架構。新版本可調整 repo 內的 skills、hooks、工具、接入設定、測試及說明；不以只修改 task-harness 或另加一份 skill 為限制。

## Solution

開發者在專案明確啟用 harness 後，agent 能從現況與需求建立驗收基準，取得可執行、可觀察的回饋，自行處理有進展的修復，並交付能追溯的結果。必要控制由可靠機制執行，困難工作按行為切片與風險處理，沒有實際需求的追蹤與角色不固定加入。

首版按缺口組合 skill、hook、工具與設定；由試行證據決定哪些機制值得保留。品質不退步是前提，人工總投入是主要改善目標。日常以 Codex Desktop app 使用；先重用已驗證的 CLI 路徑補強開發評測，再確認 Desktop 實際使用路徑。CLI 通過不代表 Desktop 通過，也不要求使用者改用 CLI。

Repo 維護共用行為、可重用工具、Codex 接入及評測資產；採用專案只提供明確 opt-in、專案契約與執行／觀測入口。發佈內容按實際 runtime 依賴選取，不把整個 repo 自動載入 agent。demo-002 是首輪採用與回放專案，不承擔共用 harness 的維護。

## User Stories

1. 作為專案開發者，我希望 agent 在實作前確認目標、範圍與重要歧義，以便減少做錯方向造成的返工。
2. 作為專案開發者，我希望驗收條件能追溯至需求與契約，以便避免程式與測試共同誤解需求。
3. 作為專案開發者，我希望 agent 檢查實際程式、呼叫端及未提交變更，以便保留既有工作並掌握影響範圍。
4. 作為專案開發者，我希望 agent 確認最低執行與觀測能力，以便及早辨識無法驗證的部分。
5. 作為專案開發者，我希望區分既有失敗、環境問題與本次回歸，以便避免修復錯誤目標。
6. 作為專案開發者，我希望 bug 修正有直接行為與相關回歸證據，以便確認問題確實改善。
7. 作為專案開發者，我希望新增功能檢查主要情境、失敗處理與重要邊界，以便降低交付缺漏。
8. 作為專案開發者，我希望重構維持已確認的外部行為，以便降低相容性退步。
9. 作為專案開發者，我希望驗證隨影響與風險升級並說明原因，以便兼顧可靠性與執行成本。
10. 作為專案開發者，我希望小修改維持簡單、中大型工作按可驗收切片推進，以便提早取得有效回饋。
11. 作為專案開發者，我希望整合完成後再檢查共同運作的結果，以便避免各切片各自通過卻整體失效。
12. 作為專案開發者，我希望 agent 在有診斷進展時自行修復，以便減少人工接手除錯。
13. 作為專案開發者，我希望無進展時收到證據、已嘗試方法與最小決策問題，以便避免無效重試與重複說明。
14. 作為專案開發者，我希望高風險修改取得獨立 review，以便補足實作者可能的盲點。
15. 作為專案開發者，我希望 review 依原始需求與產物判斷且不增加例行人工核准，以便降低協調負擔。
16. 作為任務主責者，我希望只在收益明確時委派並保留整合責任，以便取得分工效益而不丟失所有權。
17. 作為任務主責者，我希望協作時隔離寫入與共享資源，以便避免互相覆蓋或污染結果。
18. 作為專案開發者，我希望證據對應目前產物且能取回，以便自行查驗交付結論。
19. 作為專案開發者，我希望缺少必要驗證時明確得知缺口，以便不把未驗證結果誤認為完成。
20. 作為專案開發者，我希望必要條件重用可靠的自動關卡，以便減少人工反覆查核。
21. 作為專案開發者，我希望必要控制失效停止相依操作，僅能由經驗證的等效控制替代；輔助失效明示後繼續，以便兼顧必要約束與可用性。
22. 作為專案開發者，我希望持久紀錄按接續需求建立並重用宿主，以便減少額外維護。
23. 作為專案開發者，我希望恢復工作時核對實際狀態與證據，以便避免使用過時結論。
24. 作為專案開發者，我希望結果不明的操作先核對再重試，以便避免重複副作用。
25. 作為專案維護者，我希望專案明確啟用共用元件並分離專案設定，以便控制影響範圍與移植成本。
26. 作為專案維護者，我希望辨識實際使用版本並能停用與回退，以便安全比較調整效果。
27. 作為Harness 維護者，我希望先完成 Codex 整套必要能力再擴展宿主，以便避免提前建立多餘轉接機制。
28. 作為評測維護者，我希望三組使用一致的外部限制並保留各自的診斷修復策略，以便辨識完整配置的價值。
29. 作為評測維護者，我希望先以真實 bug 驗證回放方法，區分流程 smoke 與公平比較的資格，再擴大案例，以便及早發現評測本身的問題。
30. 作為評測維護者，我希望保留未用來調整流程的案例並按影響回歸，以便降低過度適配與更新退步。
31. 作為專案開發者，我希望 agent 自動整理可取得的交付、求助、重試與修復證據，不要求我計時、填表或持續觀察，以便不為量測增加日常負擔；無法觀測的人工時間保持未知。
32. 作為專案開發者，我希望可觀測的後續修復、設定與維護成本分開呈現，缺失與觀測範圍明示，以便不把未觀察到問題當成零返工。
33. 作為專案維護者，我希望先在單一專案試行再驗證第二個專案，以便區分局部成果與可移植性。
34. 作為個人 harness 維護者，我希望在同一 repo 調整 skills、hooks、工具、接入與測試，以便共同改善完整開發流程。
35. 作為個人 harness 維護者，我希望每項共用規則只有一個維護來源，以便避免多份指引與自動控制互相矛盾。
36. 作為採用者，我希望取得完整 runtime 依賴而不載入研究與答案資料，以便可靠執行並維持評測隔離。
37. 作為評測維護者，我希望 B 組以固定完整快照重現，以便新版可演進 repo 結構而不改變比較基準。
38. 作為日常採用者，我希望主要使用 Codex Desktop app，CLI 評測只在開發環境運行，以便不改變我的日常工作方式。
39. 作為日常採用者，我希望開發測試不改動日常設定、記憶、資料與既有對話／程序，以便測試故障不影響工作。
40. 作為評測維護者，我希望 grader 隨需求、fixture、依賴及環境變化按影響重驗，修正後重評固定產物，以便分辨 checker 與產品缺陷。

### 2. 術語與責任

| 術語 | 本規格定義 |
| --- | --- |
| Coding harness | 支援 agent 觀察專案、採取行動、取得回饋、恢復與交付的整套能力與約束 |
| 個人 harness repo | 共用流程、skills、hooks、工具、接入、驗證及維護說明的來源；首版聚焦 coding |
| 發佈配置 | 一組有明確版本及完整 runtime 依賴的可採用內容；不是整個 repo 的自動載入 |
| 驗收依據 | 判斷預期行為的來源，例如原始需求、可信規格、已確認契約；現行實作僅證明現況 |
| 驗證證據 | 可取回且可歸屬於受測產物的原始執行／觀測結果 |
| 行為切片 | 具有可觀察成果及有意義驗收方式的一段工作，不以檔案數或技術層硬切 |
| 必要控制 | 某操作執行前必須成立的條件；無法確認時不得執行相依操作 |
| 必要驗收 | 宣告成果完成前必須通過的檢查；缺結果不得完成，但不必阻止無關工作 |
| 輔助功能 | 摘要、統計等便利能力，其失效本身不破壞必要控制與驗收 |
| 結果不明 | 操作可能已生效，但目前沒有足夠證據確認成功、失敗或未執行 |
| 評測回放 | 固定起始狀態與驗收條件，比較不同配置；不同於日常任務的開發測試 |

| 責任層 | 所有權與最低責任 |
| --- | --- |
| Codex 宿主 | 工具執行、既有權限／隔離、原生事件與結果、session、委派與取消能力 |
| 個人 harness repo | 共用行為與實作來源、Codex 接入、必要自動控制、測試、發佈配置及維護說明；可跨既有 skills 整併 |
| 專案接入 | 啟動／測試／觀測入口、特有業務契約、資源隔離與採用版本 |
| 評測層 | 保存固定輸入與外部驗收、隔離各組、保存全部嘗試並計算結果；不能由受測 agent 自改評分標準 |

單一主責 agent 整合結果與驗收。委派不轉移最終責任，亦不自動授權建立使用者可見的新 chat。

### 3. 元件配置與專案接入契約

#### 3.0 Repo 架構與模組介面

以下為首版建議的責任劃分，描述 Module（模組）對外的 Interface（使用契約），不是五個必建套件。沿用可用的執行入口；只有真實差異或故障定位需求才新增 Seam（可替換／測試接點），不先造通用 Adapter 框架。

| 模組 | Interface：輸入、結果與失效 | 擁有的責任與限制 |
| --- | --- | --- |
| M1 開發工作流程 | 任務、授權、專案現況 → 驗收依據、修改與直接證據，或明確阻礙 | 共用判斷規則的唯一維護來源；按需使用釐清、bug／功能／重構及 review 指引；不以 skill 文字冒充強制控制 |
| M2 執行控制與證據 | 已授權操作、必要條件 → 原生結果／拒絕／失敗／結果不明及證據參照 | 優先使用宿主與專案機制；必要 hook／工具只補缺口；不另建 scheduler 或完整 runtime，不修改驗收契約 |
| M3 Codex 採用與發佈 | 選定發佈配置、專案 opt-in → 可辨識的載入／停用／回退狀態，或能力缺口 | 組裝 skills、hooks、工具與相依資源；維護版本與信任查核；不全域強制啟用、不包含評測答案 |
| M4 專案接入 | 既有專案指示、命令與業務契約 → M1/M2 可用的專案資料 | 共用規則與專案設定分開；引用既有 truth source；revision、dirty content、程序狀態於執行時取得，不複製成易過期設定 |
| M5 驗證與評測 | 固定案例、配置及直接結果 → 成果／行為／品質及可觀測成本，缺值明示 | 持有開發專用 controller、grader、回歸與全部嘗試；不進 runtime、不改日常設定，不由受測 M1 改寫判準，不要求人工觀察 |

M3 決定某專案實際載入哪些共用能力；M1 讀取 M4 並透過 M2 執行及取得回饋；M5 在受測任務之外評估產物。日常任務不依賴大型評測系統。各模組可由既有檔案及宿主能力實現，資料格式與函式介面不預先固定。

規則先有明確來源與所有者，再決定其呈現方式。Skill 說明判斷與操作，hook／工具負責可可靠判定的控制；不各自重複維護同一政策文字。既有專案必要規則不被 repo 預設覆蓋。

#### 3.0.1 Desktop 日常與 CLI 開發評測的邊界

- Desktop 是產品採用目標；CLI 的已驗證能力供開發評測使用。共用 skills 的內容驗證可以重用，Desktop 的實際載入、信任、權限、工具結果與必要控制須取得該路徑的證據。Desktop 最小日常路徑驗收須在獨立測試情境呼叫候選流程，完成一個低風險修改、相稱驗證及可追溯交付；僅列出技能或讀取檔案不算行為通過。載入、任務交付與外部取消分項記錄，前兩項及該任務必要控制通過才可宣稱此最小路徑完成，不外推所有 Desktop 能力。
- Desktop 日常 skills 的使用，與外部 controller 派送／限時取消 Desktop trial 是兩條路徑。Stop 未驗證限制依賴可靠取消的操作，不推論所有日常能力不可用；也不得藉此免除某日常操作本來需要的控制。
- 評測只使用獨立工作副本、設定與自有測試資源；優先程序內覆寫或已驗證的隔離機制。不改日常全域設定、記憶、資料，不接管既有對話、不停止其他程序。隔離盤點包含宿主自動寫入的 plugin cache、持久狀態及生成資料；程序內覆寫與設定檔未變都不能單獨證明隔離。測試寫入須落在已確認的測試專屬範圍，不覆寫日常採用的快取或狀態；事後恢復不能替代事前不干擾保證。
- 只盤點測試實際涉及的共用資源；CPU／記憶體、並行程序與共用帳號額度須有可執行的使用限制及停止條件，不新增日常背景監控或要求人工看守。具體額度在後續執行範圍內固定；未能確認資源限制或隔離時停止相依測試，不以低風險或設定檔未變宣稱零影響。
- 測試前確認資源／程序所有權及讀寫邊界，結束及失效後只收尾測試自有資源並核對無殘留；無法確認時停止相依測試。禁止靠要求使用者反覆手動 Stop 彌補控制缺口。
- 公平比較另需核對實際載入配置、共同可見材料及答案／他組產物／相關歷史的讀取隔離。Prompt「不要讀」不是強制保證；不合格僅能在必要控制有效時做流程診斷。隔離不得擴及日常作業。

#### 3.1 按需要選擇元件

- **Skill／指引：**目標理解、探索、影響分析、診斷與交付。穩定核心保持精簡，bug／功能／重構指引按需讀取。
- **Hook：**在經確認的事件與工具路徑提供上下文、蒐集事件或執行可靠檢查；不將模型評分當成唯一硬關卡。
- **腳本／工具：**可重複的環境檢查、驗證執行、產物歸屬與結果核對。原生能力足夠時不另造 wrapper。
- **設定：**專案啟用狀態、版本、指令及必要契約；秘密不得寫入套件或驗證紀錄。
- **回歸案例：**檢查成果及重要行為，不規定無關工具順序或固定 agent 數量。

以上是責任，不是必須建立的檔案清單。配套計畫的 I01–I09 將責任對應到具體改動及重用來源；需依 G01–G07 能力查核決定 hook、工具及套件的實際新增量。不預設新版必須另設一個 coding-harness skill，也不要求保留現行技能切分。首輪完成後的具體補強以配套計畫第 20 節 N01–N07 為準。

#### 3.2 最小專案接入資料（邏輯欄位，未指定格式）

| 欄位 | 要求 |
| --- | --- |
| 採用狀態與版本 | 明確 opt-in；識別共用元件版本／內容指紋與宿主版本，不依賴可漂移的名稱 |
| Root 與指示來源 | 實際 workspace、適用專案規則、當前 revision 與相關 dirty content |
| 執行入口 | 已確認的安裝、啟動、針對性測試及必要整合檢查；未知命令標未知 |
| 觀測入口 | 任務需要的工具結果、日誌、API 狀態、UI 操作或產物位置 |
| 必要條件 | 每個控制／驗收的依據、適用條件、執行者、結果判定及失效處置 |
| 執行範圍 | 允許副作用、共享資源／寫入所有權、使用者或宿主實際限制 |
| 接續需求 | 原生結果是否可取回；不足時最小持久紀錄的位置與寫入者 |
| 停用與回退 | 如何停止套件作用、切回已驗證版本及核對生效狀態；保留未完成工作的恢復資訊 |

停用 harness 不得連帶移除專案或宿主本來的必要規則。正常任務中 agent 不得自行停用關卡來完成工作。套件更新也不應默默改變已開始的試行配置。

發佈配置須列出實際啟用的 skills、hooks、工具及其 runtime 依賴，連同版本／內容指紋可重現。研究報告、歷史答案、grader 及私有紀錄不隨 runtime 配置載入。Repo 的開發用 hooks 與發佈給採用專案的設定分開管理，避免改 repo 就自動改變所有專案。拆分、重新命名或移動既有技能時，同步更新呼叫入口、相依引用、metadata、安裝／停用說明及相關測試。

B 組在任何影響其依賴的實作變更前保存完整內容及載入方式；有關 dirty content 也需納入，不能只記 HEAD。之後 C 可重構本 repo 的既有來源，B 仍從原快照執行，不讀取已改動的共用檔案。是否改名、保留相容入口或移除舊入口，依實際使用者／呼叫端盤點決定，不為比較而永久維護兩套架構。

#### 3.3 已查核的 Codex 能力與限制

以下依 2026-10-24 [官方 hooks 文件](https://learn.chatgpt.com/docs/hooks)及 [plugin 文件](https://developers.openai.com/plugins/build/plugins)；是文件事實，不是本機驗收。

| 事實 | 對設計的影響 |
| --- | --- |
| 多來源 hooks 會合併；非 managed hook 需信任目前定義，專案設定也受 trust 影響 | 核對實際載入／信任狀態，不以檔案存在當成啟用證據 |
| `PreToolUse` 可拒絕支援的呼叫，並非涵蓋所有工具；既有 exec session 的輸入不重新觸發同一前置檢查 | 逐條實測涵蓋路徑，不宣稱完整攔截 |
| `PostToolUse` 無法撤銷副作用；`Stop` 的 block 可造成續作 | 事後結果不代替事前限制；避免無進展的續作迴圈 |
| 某些不支援的回傳欄位會造成 hook 失敗但工具繼續 | 測試錯誤與失效路徑，不假設 hook 天然 fail-closed |
| Local-marketplace plugin 可由受信任專案設定啟停；安裝快取與來源可能不同 | 記錄實際載入內容；停用不等於移除檔案，版本回退需另驗證 |

命令／欄位 schema 於實作前重查。強制保證須同時具備支援、啟用、信任、涵蓋與實測有效的證據。必要控制若無法達成，列為能力阻礙並停止相依操作；只有經驗證的等效控制可替代，不得改列為建議性控制。非必要的輔助規則可以提供建議，但須明示不具強制保證。重用既有執行邊界或 CI 時，須確認其生效時機與涵蓋範圍；事後 CI 可提供驗收證據，不能代替副作用發生前必須成立的控制。

### 4. 開發與交付行為

#### 4.1 開始前

1. 確認本次是研究／規劃、實作或恢復，沿用現有授權，不自動擴張。
2. 讀取相關程式、呼叫端、規則與未提交內容；查明實際環境和必要觀測能力。
3. 選取與任務相稱的修改前檢查，區分既有失敗、環境故障與本次回歸；不是每次執行全套。
4. 建立目標、範圍、不變條件、可觀察成果與驗證方式。無法查明且會改變結果的歧義，才提出一個最關鍵問題。

#### 4.2 驗收依據與影響分析

- 每項預期結果能追溯至原始需求、可信規格或已確認契約；假設與未決事項分開。
- Agent 可以撰寫測試，但不能以待測函式算出的值作唯一預期答案，或只重述新實作。
- Bug 可行時建立舊版失敗／新版成功的回歸證據；無法重現不得冒稱已證明根因。
- 功能涵蓋主要情境、必要失敗處理及重要邊界；UI 任務依需要操作實際流程，不能只看截圖。
- 重構先確認應保持的行為，characterization 不自動把 bug 升格為正確契約。
- 修改共用介面、跨模組、狀態或影響不明時擴大驗證；說明選擇理由。專案既定必跑關卡不得因「風險低」而略過。
- 變更鎖、callback、背景工作或資源釋放時，按實際路徑檢查重入、鎖順序、資源所有權及關閉時序；可重現的高風險路徑補有時限且能收尾的測試。共用 harness 保留判斷原則，Java／Spring 等具體案例留在專案或評測 fixture，不要求所有任務跑整套併發清單。
- 需求與測試衝突先調查；不得悄悄降低驗收，修改契約須有可追溯理由及相應授權。

#### 4.3 執行與修復

小任務維持一個完整修改；中大型任務按可驗收行為切片，必要共用介面先行，不強制每片建立文件或 commit。

每次修復以原因假設、可觀察檢查及結果為依據。有新證據、縮小原因或可驗證的新方案，且符合現有範圍與限制時繼續。重複失敗且沒有進展時停止該路徑、改變策略或提出明確阻礙。不能藉微小措辭變化無限重試。

遵守實際時間／成本／工具限制；未提供額度不得虛構。需要改變需求、擴大範圍或增加權限時，先提出具體決策；繼續不受阻礙的工作。

#### 4.4 Review 與委派

涉及權限、金流、資料遷移、公開介面相容性或驗證不足的核心行為時觸發獨立 review。跨元件生命週期、鎖內呼叫外部 callback，或重要併發行為仍缺可靠驗證也屬觸發條件。此為觸發例，不是排除其他重大風險的封閉名單；不因單純出現併發相關檔案就固定增加 reviewer。

Reviewer 取得原始需求、目前產物與直接證據，自行判斷；角色分開不等於推理錯誤必然獨立。Finding 需指出具體觸發、影響與證據。Review 通過不抵銷必要驗證缺口，爭議不以無限增加 reviewer 解決。

額外委派須有明確輸入、產物、所有權與驗收方法。平行寫入須隔離檔案及 DB、port、cache、生成物等共享資源；有可能仍在寫入的 worker 不得直接被同範圍替代。

#### 4.5 證據與完成

原生結果優先。最低證據是實際輸入／命令、工作位置、受測來源（含相關 dirty content）、最終結果與可取回參照。不得虛構 exit code、hash 或把 wrapper 成功當成內層檢查成功。

來源或整合結果改變後，重開受影響驗收；各切片通過仍須檢查整合。必要項目缺證據，標為未驗證或受阻，不宣告整體完成。交付說明對照驗收條件列出結果、證據與缺口，避免複製大量日誌。

### 5. 狀態、失效與恢復

任務的待辦／執行／驗證／完成／受阻，可映射至宿主既有狀態，不要求新建狀態機。「結果不明」是**操作結果狀態**，與任務完成度、worker 是否存活分開。

| 操作結果 | 恢復行為 |
| --- | --- |
| 確認完成 | 核對產物及證據仍有效，再接續 |
| 確認失敗／未執行 | 診斷後在原授權範圍修復或安全重試 |
| 結果不明 | 查實際狀態、原始結果、operation ID 或可用冪等能力；確認安全才重試 |

無法判定且可能重複寫入或破壞資料時，停止相依操作並保留證據；其他安全工作可繼續。不能用逾時、失聯或舊 checkpoint 推斷未生效。

| 機制失效 | 行為 |
| --- | --- |
| 必要控制失效 | 不執行相依操作；修復或改用經驗證的等效控制 |
| 必要驗收失效／無結果 | 不標記完成；允許不依賴其通過的診斷或實作 |
| 輔助功能失效 | 明示缺失後繼續；若實際影響必要證據，須重新歸類 |

上述為首版要達成的行為，不宣稱僅靠 hook 已可強制。必要控制的依賴路徑必須有實測保證；無此能力時列能力阻礙。

有跨 session、多項相依或協作接續需求才持久化；優先原生可取回資訊，不為每次讀檔建立 receipt。至少保存目標、決策、完成／待辦、證據位置、阻礙及未知副作用。恢復時核對目前程式、權限、版本與活躍 worker，並遵守使用者取消。

### 6. 成效、採用與回歸

- 減少人工總投入仍是主要目標，打斷為次要目標；不要求使用者計時、填表、持續觀察或配合 7／14 天返工窗口。
- Agent 優先使用原生事件與現有產物，自動整理可取得的驗收、求助、重試、修復、交付狀態及來源參照。分清原始事件、推導統計與 agent 判讀；去除重複事件，無法確定是否屬於同一任務／返工時標未知。
- 打斷只計可確認需要人類回應或處理才能推進的事件，純進度訊息另列；記錄可見範圍，不冒稱完整人類活動。訊息間隔、等待時間及 agent wall-clock 不等於人工時間；無可靠時間來源時為 unavailable，不填零或要求使用者補填。
- 人工接手、受阻、超限、取消與驗收未過均保留，不把未完成視為省時。後續若取得修復證據可連回原任務；沒有觀察到不等於沒有返工。設定／維護成本與離線評測成本另列，不重複計入任務。
- 自動統計是輔助能力，失效明示後繼續；必要驗收證據缺失仍阻擋完成。不得為量測接管日常工作、安裝背景監控或新增人工核准。
- 品質是必要條件。只有可靠、可比的人工時間與交付品質資料才可聲稱省時；目前只判讀流程與成果，不能將代理指標換算為人工效益。
- 在開發測試環境保留少量簡單 bug、小功能與局部重構；按核心流程、模型、工具或宿主改動影響回放。檢查無必要的澄清、文件、委派及重複驗證，依任務風險判斷，不設固定工具次數或禁止 review 的門檻。
- 首個熟悉案例保留為開發案例；需要比較效果時另用未見案例及合格隔離。Desktop 為近期採用重點；第二專案、其他宿主依需求驗證，不綁成本輪完成條件。

三組共同固定外部資源上限、驗收回饋及整次 trial 補跑政策；各組內部的診斷、修復與工具重試策略屬於比較對象，保留差異並計入成本，不為統一策略而修改原生或現行組。

流程 smoke 與公平解題能力比較分設門檻。兩者都須保護原工作、滿足相依操作的必要控制、使用合格真實案例，並具備可執行驗收及結果取回能力。Smoke 可在配置或答案隔離未完全合格但實際配置及限制可辨識時檢查流程，不能據此判斷能力優劣；公平比較另須通過配置與答案隔離資格。比較有效性不足不等於可以略過必要控制。

## Testing Decisions

### 測試邊界

依已確認的完整交付、三組比較與行為驗收決策，首要測試邊界是「從使用者任務輸入到目前產物與驗證結果的完整交付」。重用 Codex 原生工具結果與專案既有檢查，不為每個內部步驟新增介面。

另對無法可靠由完整任務定位的故障，使用必要的窄邊界：專案啟停／版本辨識、hook 事件與拒絕結果、驗證工具的最終狀態、未知副作用的核對。這些是測試安排建議，具體接點待實作能力查核；不表示新增 wrapper 已定案。

好的測試應驗證外部行為、拒絕違反契約的實作，也接受契約允許的其他實作。不得要求特定類名、私有欄位、固定工具順序或逐字輸出，除非它們本身就是已確認契約。

### Grader 資格與評測控制回歸

- 新增 grader 或需求、fixture、依賴、環境出現相關變更時，按影響重驗。核對需求來源、公開使用入口及下列類型契約；有實作耦合風險時檢查合法替代解法，優先重用現有產物，不一律另寫完整解法。

| 案例類型 | 資格與驗收重點 |
| --- | --- |
| Bug | 缺陷基線因目標問題失敗，已知正確修正通過，相關正常行為維持；歷史真實案例須保留來源依據 |
| 功能 | 新增契約、必要失敗處理及既有行為有明確預期；新增契約未實現時應能被辨識，不要求存在歷史 bug 或修正 commit |
| 重構 | 修改前後均符合已確認外部契約，並核對要求的結構調整；修改前測試通過是正常情況，不製造缺陷或強迫失敗基線 |

三種類型都檢查 grader 是否會誤判合法實作，按風險使用已知結果或最小判別案例；不一律要求「歷史缺陷版＋reference 修正」。

- 資格證據綁定 grader／契約／fixture／相關環境版本；未受影響的部分可沿用，不能只因 grader 檔案未變就忽略環境改變。
- Trial 中發現 checker 缺陷，保留原結果、產物與診斷，修正升版並重評所有受影響的固定產物；不自動重跑 agent、不回送評分要求產品修到通過。結果未釐清前不記成產品失敗。Grader 正確不保證風險覆蓋完整。
- 評測 controller 回歸需拒絕子回合／錯誤 thread 或 turn 的完成事件，保留快速抵達的正確事件；結果不明查原生狀態，確認 writer 停止後才續作，沿用原截止時間與全部成本。正常取消、失聯收尾及不影響無關程序均需證據；只存在於 M5，日常有相同需求再抽共用能力。

評測補強先保留已確認缺陷的最小回歸及可重用控制邏輯，沿用原生操作與既有檢查。只有重複操作形成實際需求時才增加薄的執行入口；不要求集中於同一檔案，也不以先完成整合評測工具作其他驗證的前置條件。

### 測試範圍與既有範例

- 共用工作流程、Codex 接入、專案採用與恢復、驗證證據及評測隔離都需有相應情境。
- Repo 整合驗收涵蓋 M1–M5 的實際呼叫與相依內容；重用元件也須在新組裝方式下驗證。主測試 seam 仍是完整任務交付，啟停／回退、可靠控制及證據取回沿用既定窄測試接點，不為每個邏輯模組另造測試框架。
- 首輪應用模組是 concurrent-request-scope。既有 property、scope creation 與 TTL cleanup 測試可作為測試風格及相關回歸參考。
- TTL cleaner 案例已完成 V2 資格驗證及三組 smoke；既有 TTL 測試不能替代 shutdown 驗收。B 後續確認的 factory-close 死鎖作為專案失敗案例保留，不修原 trial、不推論由舊 skill 造成。實際證據見配套計畫第 19 節。
- 設計階段未執行測試；下表為驗收要求。後續已執行的局部測試及尚未驗證的 hook／Desktop 能力，見配套計畫執行紀錄。

| 情境 | 必須觀察到的結果 |
| --- | --- |
| 未啟用專案 | 不載入候選流程／hook；既有宿主及專案控制仍在 |
| 啟用、更新、停用與回退 | 可辨識實際載入版本／信任狀態；停用及回退可驗證，其他專案與未提交工作不變 |
| 發佈配置與 repo 重構 | runtime 依賴完整、入口與引用一致；未採用專案不受影響；研究／答案不隨包載入；B 快照不受 C 修改影響 |
| 正常小修改 | 有相稱驗收與直接證據；agent 依風險辨識不必要的澄清、文件、委派或重複驗證，不固定工具次數 |
| 評測不干擾日常 | 使用獨立副本／設定／自有資源；宿主自動寫入亦在測試範圍，日常快取／持久狀態不被覆寫；CPU／記憶體、並行程序及帳號額度限制有效，成功／失效後日常作業不受測試干擾 |
| 主／子回合及原期限續作 | 只接受指定主 thread／turn，未知狀態先核對、writer 停止才續作，不重設期限、不誤清理其他程序 |
| Grader 或其相關輸入變更 | 依影響重驗資格；checker 修正升版重評固定產物，保留原結果且不重跑 agent |
| 併發／生命週期風險 | 適用路徑有重入、鎖順序或釋放時序檢查；高風險有界測試及必要獨立 review，無例行人工核准 |
| 自動證據不足 | 輔助統計標缺值／觀測範圍，不要求使用者計時、填表或觀察；必要驗收缺證據仍不得完成 |
| Desktop 實際使用與外部控制 | 分項記錄載入、低風險任務修改→驗證→交付及外部取消；載入成功不能代替行為驗收，CLI 證據不冒充 Desktop，Stop 缺口只阻擋相依操作 |
| Bug／功能／重構資格 | 按類型驗收；bug 重現缺陷、功能檢查新增契約、重構維持外部契約，不將 bug 的失敗基線強加所有案例 |
| 需求歧義／錯誤預期 | 查明依據；重大未決問題才詢問，不從錯誤實作產生自我證明 |
| 修改共用契約／高風險路徑 | 擴大相關驗證並觸發必要 review；缺檢查不得完成 |
| 舊證據後再修改 | 不接受過期通過結果，重驗受影響項目 |
| Hook 未信任、逾時、錯誤回傳／工具路徑未涵蓋 | 不誤報為有強制保證；必要控制不足時不執行相依操作，不以建議或事後檢查取代事前控制 |
| 結果不明／恢復 | 核對實際結果，不重播可能已生效的 mutation |
| 中斷／取消／worker 失聯 | 尊重取消；確認存活與寫入權，無法確認就不重疊派工 |
| 輔助統計失效 | 明示缺失後繼續，不把缺值填成零 |
| 三組最小回放 | 相同基線及驗收、可區分實際配置、保留全部結果；隔離不合格僅報流程 smoke，不作能力優劣比較；單案例不推論普遍效益 |
| 三組修復策略不同 | 共用外部上限、驗收回饋與 trial 補跑政策，保留組內策略差異並計入成本 |
| 受阻、超限或人工接手 | 並列交付狀態與可取得成本；人工時間不可得則標未知，不要求補填；原 trial 結果保留，不把未完成視為省時 |

## Out of Scope

### Boundaries

本輪僅授權同步修訂此規格與配套計畫、整理改動清單及檢查一致性；不得修改 skill、hook、程式、設定，不執行測試試行、不更新套件快取、不 commit／push／PR／部署。首輪實作與 smoke 已完成，歷史授權及上限不自動延伸為下一輪執行授權。

首版先支援 Codex，再驗證其他宿主。通用規則與宿主／專案設定分離，但不預先建置通用轉接框架。按需求新增 skill、hook、腳本或工具；不要求每類都新增元件，也不預設 MCP server、scheduler 或獨立 agent runtime。

後續實作範圍可以涵蓋整個 repo，包括入口說明、技能編排、共用工具、Codex 接入、測試及發佈配置；本輪只提出後續改動，實際執行須依後續授權，歷史進度見配套計畫。未受首版影響的技能、歷史研究與既有功能不順手重寫；不因 repo 定位擴大而將首版擴展成所有 AI 工作類型。

不增加例行人工核准點；既有授權、安全與專案必要關卡仍適用。不可把「減少人工介入」解讀為擴大寫入權限或自行降低驗收標準。

不在本輪建立 glossary、ADR 或 issue；本規格內的術語表供本次設計使用。既有文件與未提交工作不搬移、不覆寫。
