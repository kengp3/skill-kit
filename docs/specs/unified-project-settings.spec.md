# 統一專案設定、模型主導任務流程與模型分工實作規格

日期：2026-10-25。狀態：依對話與 ADR 整理的實作規格；尚未實作或執行本版驗收。本文的「必須」描述目標行為，不表示現行版本已具備該能力。

依據：[設定整合 ADR](../adr/0001-unified-project-settings.adr.md)、[任務合約用語](task-harness-glossary.spec.md)及本輪逐題確認。後續決策取代早期提案：成功移轉後刪除舊設定、不保留備份；預設模型回退自動生效；hooks 不可用時由模型接手；模型清單採分號連接推理強度。實作不得恢復被取代的舊要求。

## Problem Statement（問題）

使用者需要在專案內安裝、設定及使用 task-harness，但目前文件規範與 harness 設定分成兩份，且日常流程依賴 Python handler。設定、宿主事件、任務判斷與執行環境資格混在一起，增加初始化、移轉與修復成本，也違反「主要使用模型能力，外部工具與 runtime script 僅為選配」的設計。

現有模型分工還缺乏完整的專案設定介面，無法清楚表達各階段、任務與 agent 角色的首選模型、推理強度及替代順序。主責對話的模型選擇、子 agent 的實際模型與單次任務指定也需要明確分開。

本輪讀取的現行來源顯示：project-setting 已使用獨立 Markdown 文件與提示型 hooks；task-harness 的接入規則仍要求三個 hooks、Python 與環境資格，封裝仍直接呼叫 Python handler，舊讀取器仍使用 harness-project.json。相關 review 報告規則亦有必跑 Python checker 的文字，可能構成間接依賴。這些是待修正的現況，不是新規格的例外。

## Solution（方案）

本輪一併交付三項調整：

1. 以 project-setting.md 作為專案長期設定的唯一來源；project-setting 可獨立使用，只有指定包含 task-harness 或由 task-harness 委派設定時，才依其規格設定相關內容。
2. 以模型執行核心判讀、推進與驗收。hooks 作為標準事件觸發機制；不可用時先診斷與修復，仍無法使用則由主責模型在相同檢查時點接手，維持同一份任務合約與完成標準。
3. 支援依任務、agent 角色、階段與專案預設選擇模型，使用有序模型清單、各模型推理強度及自動預設回退；記錄實際執行者與可查證的生效結果。

任務合約是任務狀態與單次覆寫的權威來源；project-setting.md 是專案長期設定的權威來源；技術收據只是實際事件的觀測紀錄。三者不互相替代，不因檔案存在就推定授權、環境合格或成果完成。

## User Stories（使用者故事）

1. 作為專案使用者，我希望單獨使用 project-setting 管理文件規範，以便不採用 task-harness 時仍可正常工作。
2. 作為專案使用者，我希望指定包含 task-harness 後才加入其設定，以便清楚控制採用範圍。
3. 作為任務使用者，我希望啟動 task-harness 時自動診斷缺失設定並交給 project-setting 初始化或修復，以便在原授權內繼續任務。
4. 作為技能維護者，我希望 task-harness 提供自己的 Markdown 設定規格，以便 project-setting 不必內建其專屬邏輯。
5. 作為專案使用者，我希望長期設定集中於 project-setting.md，以便不再同步另一份 JSON 設定。
6. 作為專案使用者，我希望任務合約與技術收據的路徑取自既有文件分類表，以便只有一份路徑規範。
7. 作為既有使用者，我希望移轉保留現有產物位置，以便舊合約與證據仍可查找。
8. 作為既有使用者，我希望移轉前收到提示、成功驗證後刪除舊設定，以便不保留兩份有效設定。
9. 作為既有使用者，我希望移轉失敗或衝突時保留原檔並回報，以便不遺失尚未移轉的內容。
10. 作為使用者，我希望舊環境資格只作歷史資料，以便新流程不誤用舊的已通過狀態。
11. 作為設定維護者，我希望表格容許列順序與空白調整，以便正常整理文件不改變設定語意。
12. 作為設定維護者，我希望必要欄位缺漏、重複或無效時依規格處理，以便模型不自行猜測設定。
13. 作為任務使用者，我希望停用所有選配腳本與外部輔助工具後仍可使用核心流程，以便不被 runtime 安裝要求阻擋。
14. 作為任務使用者，我希望 hooks 失效後由主責模型接手相同檢查，以便任務持續推進。
15. 作為任務使用者，我希望 hooks 恢復時自動銜接目前進度，以便不重做操作或重複派工。
16. 作為任務使用者，我希望狀態不明先查明、條件改變才重驗，以便避免重播副作用並保留有效證據。
17. 作為使用者，我希望 task-harness 尊重目前對話的主責模型，以便階段設定不自行切換我的對話模型。
18. 作為使用者，我希望手動切換對話模型後，後續繼承主責的派工跟隨最新選擇，以便我的選擇生效且不中斷既有 agent。
19. 作為專案使用者，我希望分別設定規劃、執行、驗證、審查及自訂階段，以便依工作需求安排模型。
20. 作為專案使用者，我希望階段設定不強制所有任務走完固定流程，以便小任務保持簡單。
21. 作為任務使用者，我希望本次指示、任務、角色、階段與專案設定有明確優先序，以便可預期地選擇模型。
22. 作為設定維護者，我希望用模型清單與分號強度格式表達首選及替代，以便調整順序時不配錯模型與強度。
23. 作為使用者，我希望未填模型或清單耗盡時按既定規則回退，以便不必特別填寫 default。
24. 作為使用者，我希望不支援的推理強度可回退宿主預設，以便優先保留指定模型；明確禁止變更時仍遵守我的限制。
25. 作為使用者，我希望所有候選都不可用時只暫停受影響工作，以便其他工作繼續。
26. 作為使用者，我希望單次模型指定只保存在任務合約，以便恢復同一任務時有效，新任務不意外繼承。
27. 作為使用者，我希望明確要求設為專案預設才變更長期設定，以便執行中的替代結果不污染專案設定。
28. 作為任務使用者，我希望無法建立子 agent 時由主責模型循序接手，以便不需外部派工工具也能繼續。
29. 作為驗收者，我希望獨立審查不能以主責自我檢查冒充，以便必要的獨立性缺口保持可見。
30. 作為驗收者，我希望看到實際執行者、模型與直接證據，以便分辨設定意圖與真實執行結果。
31. 作為安裝者，我希望技能、Codex plugin 封裝與本地安裝／升級指南同步，以便安裝結果符合本版設計。
32. 作為使用者，我希望改版在隔離專案驗收且不改動其他專案或全域安裝，以便既有工作環境不受測試影響。

## Implementation Decisions（實作決策）

### D1. 職責與交付介面

| 元件 | 責任 | 不得承擔的責任 |
| --- | --- | --- |
| task-harness | 提供設定規格、有效性、移轉／修復規則；主導任務與驗收；診斷後委派設定並再檢查 | 不把核心判讀委託給必要外部 dispatcher、parser 或 validator |
| project-setting | 依指定規格編輯設定、保留無關內容、檢查寫入邊界、讀回核對 | 不內建 task-harness 專用欄位、預設值、移轉或業務判斷 |
| 主責 agent | 唯一任務協調者及語意合約寫入者；派工、證據核對、恢復與收尾 | 不以 worker 宣稱、hook 回應或設定值直接宣告成果通過 |
| hooks | 依宿主能力在關鍵時點觸發同一套流程要求 | 不改寫產品或設定、不產生新授權、不代替成果判斷 |
| 選配工具與腳本 | 提供輔助證據或自動化 | 缺失時不得阻擋核心流程或間接阻擋 review |

task-harness 隨技能維護一份 Markdown 設定規格，包含欄位、預設值、範本、有效性、驗證、移轉及修復規則。包含 task-harness 的設定入口將這份規格提供給 project-setting，由模型讀取。project-setting 只提供通用的「依指定規格設定」流程，不需額外註冊服務或腳本。規格文件不是第二份專案實際設定。

須同步調整受影響技能、參照規則、範本、封裝、驗證案例及指南；間接依賴也在範圍內。例如 review 規則不能把選配的 Python 核對器保留為日常交付門檻。工具不可用時仍須如實標示無法核對的證據，不能改用模型猜測 hash 或測試結果。

### D2. 設定位置、格式與寫入邊界

- 專案長期設定統一放在 project-setting.md，不再維護 harness-project.json，不在 Markdown 內嵌另一份 JSON 專案設定。
- 單獨使用 project-setting 不要求載入 task-harness，也不加入其專用設定或 hooks。安裝技能與初始化設定不等於啟用個別任務。
- 包含 task-harness 時，在既有「類型／文件用途／目的地與檔名」表新增 task-contract 與 hook-receipt；兩列為唯一路徑來源，不另維護 contract_dir 或 receipt_dir。
- 保留既有分類與其他設定；移轉沿用既有合約及收據位置，不搬移或重新命名產物。
- 其他設定採 task-harness 定義的固定 Markdown 表格，現有共識為 Task Harness 區段的「設定項目／值」形式。模型有序清單作為設定值；不採每個候選模型各一列加數字順序的提案。
- 表格列順序與空白可調整；清單內的候選順序具有語意，不可任意重排。識別用的區段、欄位名稱與格式由 task-harness 規格明確定義。
- 必要欄位缺漏、重複或無效時，task-harness 診斷後交由 project-setting 依規格修復；遇到內容衝突先回報，不猜測或擅選值。
- 根目錄須由使用者或工作階段確認，遵守專案規範與授權；寫入檢查路徑與符號連結邊界，保留無關設定，完成後讀回。唯讀或禁止設定變更的任務仍遵守該限制。
- 本次不重新設計整份任務合約的序列化格式；「不內嵌 JSON 專案設定」不等於已決定移除既有任務合約的所有結構化區塊。

### D3. 初始化、修復與一次性移轉

啟動 task-harness 後先檢查設定。缺失、舊格式或錯誤設定分別交給 project-setting 初始化、移轉或修復，再由 task-harness 核對並繼續相依操作。設定由 agent 操作，hooks 不自行改寫。

可在原授權內完成的診斷與修復主動進行，不新增例行核准點；需要人工操作或超出授權時回報所需行動，僅暫停真正依賴該操作的工作。衝突仍先回報，不以自動修復為由選擇使用者尚未決定的值。

一次性移轉必須先提示，依提供的規格合併舊值並保留無關內容。刪除舊設定只有三項門檻，三者須全部成立：

1. 新設定成功寫入，與舊設定逐項對帳無遺漏。
2. 通過 task-harness 規格的格式及內容驗證。
3. 目標執行版本支援新格式，且經正常使用流程實際讀回成功。

通過後刪除已移轉的舊設定，不留備份、不長期雙讀。不刪除合約、收據或其他產物。移轉失敗、讀回不明或內容衝突時保留原檔並回報；不能只因存在舊 JSON 就默默停用。中斷後先核對已寫入及尚未刪除的狀態，不把未知結果當成功，也不盲目重做。

舊環境資格僅保留歷史舊值及處理結果，不直接成為新流程的已驗證資格。宿主信任與環境能力依本次診斷另行檢查、回報，不增加上述刪檔門檻。格式移轉通過不代表 hooks 已可用；hooks 不可用時按 D4 接手。

### D4. 模型主導、hooks 接手與恢復

核心不得依賴任何 runtime script、外部 CLI、MCP 服務、外部判讀器或派工器。換語言、內附 runtime 或把腳本藏在 helper 後方，不構成解除依賴。開發端封裝與測試工具可使用 Python，但使用者日常流程不需執行 Python 建包。宿主既有的檔案操作及 agent 能力是使用介面；本限制不代表模型可取代個別任務必要的真實操作或測試。

hooks 為標準接入機制，不可只因模型可接手就省略接入工作。失效、缺失或宿主不支援時，先在原授權內診斷及嘗試修復，設定變更交給 project-setting。仍不可用時，自動由 task-harness 的主責模型接手，不退出、不因該原因暫停整個任務，也不新增切換模式的同意步驟。

兩種觸發方式共用同一份任務合約與檢查規則：

| 時點 | 主責檢查內容 |
| --- | --- |
| 開始或恢復任務 | 設定、授權、進度與下一步 |
| 派工或切換階段前 | 前置條件、負責 agent 與模型 |
| agent 回報後 | 成果、證據與任務狀態 |
| 準備結束前 | 逐項完成條件；仍有可執行的必要工作就繼續 |

確認 hooks 實際恢復後，自動按合約與現有證據銜接，不重啟任務、不重做已完成操作、不重派已啟動 agent。狀態不明先查明，成果或條件改變才重驗受影響項目；單純恢復或重複觸發不是重做理由。

記錄實際 hook 狀態與接手方式。模型主動檢查不等於宿主機械攔截，不保證舊 Python handler 的原子收據或一次性控制仍存在；沒有觀測到的事件不能生成冒充實際 hook 執行的技術收據。事件注入、條件阻擋及續作能力須分別驗證。

### D5. 任務合約、授權與證據不變條件

沿用唯一合約、主責唯一語意寫入者及既有成果／依賴／恢復概念，不建立第二份接手模式狀態。重要結果、授權或範圍變更、交接與正常收尾須保存並讀回；保存失敗或不明時核對同一份合約，暫停真正依賴該更新的操作，不另建替代合約或重播產品操作。

使用者停止、取消、唯讀、討論限定、實際任務阻礙及宿主權限仍有效。hooks 或模型接手不擴大授權，hook 產生的續作不冒充新的使用者授權；明確 Stop 不抵抗，也不為補寫紀錄而繼續執行。恢復時核對現況、原操作結果及 agent 存活狀態，不把 timeout 或斷線當作未執行。

主責只在所有必要成果與適用驗收均有目前證據時宣告完成；獨立審查缺口、未知副作用或必要測試未執行不能標成完成。不因可選工具缺失阻擋核心流程，也不因此降低成果的驗收要求。

### D6. 模型設定範圍與階段

專案長期預設、角色與階段規則由 project-setting 依 task-harness 規格維護。單次任務的模型、強度與替代安排僅存於任務合約，恢復同一任務仍有效，新任務不沿用。只有明確要求設為專案預設時才更新長期設定；實際回退結果不自動改寫原指定或專案設定。合約記錄本次覆寫及實際結果，不複製全部專案設定。

預設階段為規劃、執行、驗證、審查：分別負責需求／方案／拆解、成果產出、檢查與驗收證據、品質／風險／遺漏評估。可自訂階段，不要求每個任務走完全部階段，不預綁模型，也不要求每個小步驟建立 agent。

主責沿用使用者選定的對話模型，task-harness 不依階段自動切換主責。不同模型的任務交由宿主支援的子 agent 執行。使用者途中手動切換對話模型後，後續繼承主責的派工跟隨最新模型及推理設定；已啟動 agent 保持原設定，不重啟或改派。既有效的明確任務、角色、階段及專案設定不因此被覆蓋。

### D7. 模型選擇、候選清單與推理強度

首選依序取自：本次使用者明確指定、個別任務設定、agent 角色設定、任務階段設定、專案預設模型。全部未設定才沿用主責。「未設定」與「已指定但不可用」必須分開。

候選清單格式為 `[模型A;high, 模型B;medium]`。逗號分隔候選，分號連接模型與強度；第一項是首選，其後依序替代。可省略強度，例如 `[模型A;high, 模型B]` 或 `[模型A, 模型B]`。此為已確認的設定語法，不是目前帳號的模型或強度推薦。

| 情況 | 必須採用的行為 |
| --- | --- |
| 明確指定模型、未指定強度 | 使用宿主對該模型的預設強度 |
| 完全沿用主責 | 沿用主責當前模型與強度 |
| 切換替代模型 | 使用該候選自己的強度，不複製前一模型強度 |
| 模型可用、強度不支援 | 優先保留模型，改用該模型的宿主預設並記錄原因；仍無法啟動才換下一候選 |
| 使用者明確禁止改變強度 | 遵守限制，不自行降低或改用預設 |
| 首選及替代均不可用 | 自動執行末段預設回退，不需使用者填 default |
| 預設回退 | 有專案預設就使用它；沒有專案預設才沿用主責 |
| 包含預設回退仍不可用 | 暫停該項工作並詢問，其他不受影響工作繼續 |
| 啟動結果不明或逾時 | 先核對 agent 是否已執行，不盲目重派 |

清單可明列最後一項 default，但省略時行為相同。同一次選擇／回退不重複嘗試相同模型；D7 明確允許的強度修正不是再從清單重頭嘗試。不得因專案預設失敗，就擅加「一定再試主責」的新規則；也不把低優先序的角色或階段設定自動串成替代鏈。

記錄請求模型、強度、選擇依據、替代原因與宿主實際回報結果。宿主不能提供實際模型或強度證據時，標示未知／未核實，不把設定字串當實際執行結果。宿主的角色限制或固定模型優先序不得以文字宣告繞過。

### D8. 無法派工時的接手

宿主無法建立子 agent 時，先在原授權內診斷及嘗試修復；仍無法派工，由主責依原任務分工循序接手並記錄實際執行者與模型，不引入外部派工工具。這與「指定候選模型不可用」分開處理，不用此規則繞過 D7 的候選耗盡處理，也不聲稱主責已切換成指定模型。

明確要求獨立 agent 審查時，主責自我檢查不得視為已滿足；該條件保留未完成並回報，其他工作繼續。不自動刪除或降低獨立審查要求。

### D9. 封裝與本地安裝／升級交付

實作交付須同步技能、規格、範本、既有 Codex plugin 封裝及本地安裝／升級指南。封裝不能仍把舊 Python handler 或舊設定檔保留為核心前提。指南須分清來源維護工具、可選輔助工具與使用者正常流程，涵蓋首次設定、指定包含 task-harness、移轉、模型設定、hooks 診斷／接手及能力限制。

全新安裝及舊版升級在隔離測試專案驗收，辨識實際載入的來源與版本。不得改動其他既有專案或全域安裝；不把歷史候選、舊名 plugin 或舊環境的通過結果直接算成本版驗收。

## Testing Decisions（驗收決策）

### 驗收邊界與既有方法

主要驗收邊界沿用已確認的「使用者啟用技能 → 模型／宿主執行 → 設定與任務產物 → 讀回核對」完整流程，測試可觀察行為，不以內部函式數量或固定措辭作成果證明。真實 agent 執行是本輪最低門檻，離線測試作補充。

可沿用的既有方法包括：project-setting 的獨立安裝與檔案前後比對測試、harness 的封裝入口測試、任務合約與結果不明的邊界案例、歷史 H05 的實際 agent／中斷／恢復驗收，以及新名稱 plugin 的隔離載入紀錄。既有測試中「必要 Python／hooks」等舊斷言須依本規格改寫；不因舊測試要求而保留被取代的產品行為。本次僅查閱，未重跑或認定它們已通過新要求。

### 最低驗收矩陣

所有案例目前狀態皆為「未執行」。下列七組均為必要範圍，子情境不可用單一成功路徑代替。

| ID | 情境／輸入 | 預期可觀察結果 | 必要證據 |
| --- | --- | --- | --- |
| A | 僅提供 project-setting，未指定包含 harness；初始化及更新既有規範 | 無 task-harness 依賴、專用設定或專用 hooks；其他內容保留 | 實際 agent 紀錄、安裝內容及設定前後讀回 |
| B | 明確包含 harness；分別測缺失、有效、缺欄、重複、無效值、列順序／空白變動 | 按 task-harness 規格初始化／修復；不猜測；保留無關內容；分類表為唯一路徑來源 | 規格來源、操作紀錄、前後檔案與正常流程讀回 |
| C | 舊設定：成功、衝突、寫入／驗證／讀回失敗及中斷後恢復 | 三門檻全過才刪舊檔；失敗保留；不留雙有效設定；產物不搬移；舊資格僅作歷史 | 舊值對帳、三門檻逐項結果、檔案存在狀態、產物位置及資格診斷紀錄 |
| D | 所有選配 runtime script 與外部輔助工具停用；完成含必要驗收的小任務 | 核心依模型能力完成；不要求安裝或暗中呼叫替代腳本；review 不因 helper 缺失被間接阻擋 | 依賴停用證據、實際工具／agent 軌跡、合約、成果與驗收證據 |
| E | hooks 正常、失效、修復不成功、途中恢復、重複觸發及狀態不明 | 同規則／同合約／四時點檢查；自動接手與銜接；不重播副作用、不重派；條件變更才重驗 | 真實事件與接手紀錄、agent 身分、可核對的操作次數／產物、前後合約 |
| F | 各層優先序、清單順序、未設定、耗盡、自動 default、同模型去重、強度缺省／不支援／禁止變更、途中切換、任務恢復與新任務 | 符合 D6–D7；既有 agent 不重啟；單次設定不污染專案；實際回退可追溯 | 請求及實際模型／強度證據、失敗原因、派工身分、任務與專案設定前後對帳 |
| G | 宿主無法建立子 agent；分別含一般工作與明確獨立審查要求 | 主責循序接手並記錄實際模型；獨立審查保持未完成；無關工作繼續 | 派工失敗／診斷紀錄、實際執行者、成果及保留未完成的驗收項目 |

A–G 的整體驗收須涵蓋隔離專案全新安裝與舊版升級。另跨案例核對：唯讀與 Stop 不被接手繞過；產品／合約／設定無越界寫入；使用者停止或未知結果不被當成自動重試授權；其他既有專案及全域安裝不被變更。

每個案例採「預期 → 實際觀察 → 證據位置 → 判定」記錄，保留候選版本、宿主版本／介面、任務身分、實際執行模型可取得程度、產物與驗收依據。失敗、受阻、未驗證與通過分開標示。部分平台不可測不代表整版已驗收；保留限制及受影響項目。
