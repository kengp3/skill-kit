TASK HARNESS / OPERATING GUIDE / 2026-10-02

把需求拆成可驗收的工作，讓執行與續作都有依據。

一個 coordinator 維護權威任務清單，依條件分派工作，讀取實際產物，再接受完成結果。工具負責執行；skill 提供協調、驗收與恢復規則。

依本專案 task-harness 現行內容繪製。淺灰底／橘色重點；兩張 doc-wide 靜態圖。窄螢幕可在圖內水平捲動。

01 / ENTRY

先決定這次要做到哪裡

模式入口行為交付與停止點
plan-only讀取現況，拆分工作，寫出依賴與驗證方式。交付計畫後停止；不開始實作，不啟動 worker。
execute建立或沿用計畫，挑選就緒工作並執行。全部驗收通過，或記錄無法安全繼續的阻礙。
resume先核對既有清單、產物與存活 worker，再接續。沿用原有權限；續作不會增加外部操作授權。

「規劃並執行」可在計畫建立後接續工作，不強制加入一個新的批准關卡。只有結果會改變、無法安全推論的缺口，才需要確認。

02 / EXECUTION LOOP

以任務清單為中心，逐輪推進

先讀實際檔案、專案規範、現有修改與工具能力；再確定目標、可寫範圍及 Definition of Done。新任務建立清單，續作任務先對帳，之後才進入同一個執行迴圈。

圖一保留主要決策；resume 的對帳細節見第 07 節。沒有安全就緒任務、取消或明確限制耗盡時，保存 checkpoint 並說明阻礙，不繼續空轉。

一份狀態來源

沿用既有 tracker 或專案允許的計畫檔。coordinator 是共同清單的唯一寫入者，worker 回報成果，避免多人互相覆蓋狀態。

接受結果，才解鎖依賴

完成一項工作後，立刻檢查是否有新任務就緒。獨立任務不必等所有 worker 一起結束，也不能跳過必要的整合驗收。

03 / TASK CONTRACT

每項任務都要能被接手、執行與驗收

先理解實際受影響的流程，再依可驗收成果拆分。保持一個任務能在有限上下文內理解與完成；檔案數和時間只是線索，不是硬性門檻。獨立成果可拆開，小而連貫的修改不必拆碎。

紀錄內容它解決的問題例子（示意）
ID、成果、依賴任務是否可辨識、何時能開始T2 完成訂單查詢；依賴 T1 的 API 契約
Owner、handle、attempt誰正在處理、如何查詢或接手保存工具實際回傳的 worker handle；不虛構 agent 身分
可寫範圍、共享資源能改哪裡、是否和其他工作衝突後端模組、測試資料庫、生成目錄與 port
Acceptance、Verify什麼算成功、用什麼直接證據確認輸入非法金額必須拒絕；執行指定測試並核對結果
狀態、Evidence、版本目前進度及證據是否仍適用命令、退出碼、產物路徑、revision 與 dirty files 或指紋
Blocker、下一步遇到中斷時不用重新猜測缺測試憑證；取得後重跑指定案例

派工前檢查缺漏的依賴 ID、自我依賴及循環。需要調整任務時記錄理由與受影響項目；不能刪掉需求或改弱測試來製造完成。

04 / READY TO DISPATCH

pending 只表示未開始；就緒需要另外判斷

開始之前，五個條件都要成立

  1. 依賴已 done，而且完成證據仍適用。
  2. 必要的輸入、契約與產物已存在。
  3. 操作仍在使用者授權與 host 限制內。
  4. 可寫檔案與共享可變資源沒有衝突。
  5. 沒有舊 worker 仍可能寫入相同範圍。

條件具備後，才考慮委派是否有幫助。工具不可用或不允許委派時，coordinator 串行完成並如實記錄 owner。

Worker 收到的是可執行契約

Task ID / outcome
Inputs: workspace、規範、來源、依賴產物
Ownership: 可改檔案與排除範圍
Acceptance / verification: 行為與直接檢查
Limits: 授權、資源限制、停止條件
Return: 產物、命令結果、版本、未解問題

保留他人修改；不自行更新共同任務清單；
未受指派時不再向下委派。

同檔案、資料庫、lockfile、輸出目錄或 port 都可能形成衝突。選擇單一 writer、真正隔離資源，或改為串行。Git branch 名稱本身不提供檔案系統隔離。

05 / ACCEPTANCE & STATE

產物回傳之後，還有一道驗收關卡

Worker 回報成功只代表有待檢查的結果。coordinator 讀取實際產物與 diff，檢查行為，並在最終工作環境驗證組合後的成果。當風險或主觀品質值得額外評估時，才使用獨立 evaluator。

圖二是任務清單的五種狀態。取消與 host 預算耗盡是本次執行的停止條件，不在此另造 cancelled／failed 狀態。圖中將解除阻礙後的重查，表達為回到 pending。

pending
尚未開始，或有理由重新開啟。仍需通過就緒檢查。
running
coordinator 正在做，或派工已成功啟動；派工失敗不算 running。
verifying
產物存在，但驗收或整合尚未完成；測試正在執行也不能先標 done。
done
目前產物通過適用的驗收與整合檢查；worker 的舊綠燈不能代替最終版本。
blocked
記錄缺少的輸入、權限、外部條件或待診斷原因，並指出具體解除方式。
證據必須綁定受測版本。輸入或產物改變時，重新驗證受影響行為與下游依賴；無關改動不必觸發全面重跑。
06 / VERIFIED EXAMPLE

一次真實分派：完成 receipt helper

以下是建立 skill 時的隔離驗證案例，實際採用一名 worker。兩個 helper 的修改足夠集中，沒有為了併行而強行多拆一個 agent。

任務負責者與可寫範圍驗收與依賴
T1 完成 helperWorker 修改 prices.py、labels.py加總非負整數分幣；拒絕 bool、非整數與負數；名字去空白，空名用 Guest
T2 驗證 receipt 整合Coordinator 核對 receipt.py、更新計畫及 evidence依賴 T1；驗證組合輸出、非法輸入傳遞及受保護檔案不變
  1. coordinator 建立單一計畫並記錄原始檔案指紋。
  2. 成功派工後記錄工具回傳的 /root/eval_execute/helpers handle。
  3. worker 回傳後，coordinator 讀取程式並執行 check.py 與額外整合測試。
  4. 既有 receipt.py 已正確呼叫 helpers，因此保留原狀；驗證通過後才接受 T1、T2。

結果與命令：[本地證據] receipt helper 驗證紀錄。此案例驗證分派與整合，不是多 worker 同時寫入壓力測試。

什麼情況才值得平行？

例如 API 契約確定後，前端畫面與後端處理可由不同 worker 負責，前提是可寫檔案和測試資源互不衝突；整合驗證則等待兩者完成。這是操作示意，並非上述 fixture 已測情境。

07 / CHECKPOINT & RECOVERY

接續工作，從核對現況開始

每次有重要成果被接受，或準備交接、結束 session 前，保存 checkpoint：任務狀態、產物位置、worker handle、驗證版本、已知失敗、未知結果的操作與下一步。記錄不包含憑證或不必要的敏感輸出。

續作時的順序

  1. 重讀指示與權威任務清單，確認原有範圍。
  2. 核對當前檔案、修改與存活 worker。
  3. 找出過期證據、未完成工作與未知副作用。
  4. 完成對帳後，挑選下一項安全就緒任務。

清單寫著 running 不代表 worker 還活著；沒有新訊息也不能推定它已死亡。重派前確認舊 worker 停止，或隔離新的寫入範圍。

實測案例：兩種誤判都被擋下

過時完成紀錄：原本 T1 標為 done，但現在的 double(3) 測試失敗。agent 重開 T1，將 value + 1 修為 value * 2，再重新驗證。

逾時寄送：T2 的回應逾時，但 fixture 的權威紀錄已顯示一筆寄送。agent 查明結果後沒有再次呼叫寄送程式。

查看 resume 驗證紀錄。這是本地 fixture，沒有驗證真實寄送服務。

逾時代表結果未知。先查 receipt、operation ID 或權威狀態；可用時採服務的 idempotency 機制。若重要副作用仍無法安全確認，block 該任務並取得必要決定，不盲目重送。

08 / DONE & STOPPING

完成要有證據；停止要能接手

重試與停止

沿用 host 的有限重試政策。若沒有，安全的暫時性操作在核對狀態後最多再試一次。實作驗證失敗先診斷、作針對性修正；沒有新證據時不反覆嘗試同一失敗。

取消、明確預算耗盡、授權邊界未解或無安全就緒工作時，停止新增派工、保存 checkpoint。需要停止 worker 時使用現有控制；若無法確認停止，明確揭露。

整體交付

逐項對照使用者要求、任務清單及最終整合產物。全部 Definition of Done 通過才宣告整體完成；否則列出已接受成果、未驗證項目、blocker 與精確續作步驟。

Skill 本身沒有背景 scheduler、原子鎖或 exactly-once 保證；session 結束後不會自行喚醒。需要那些能力時，必須由 host 或另行授權的系統提供。

已驗證：只規劃、實際分派整合、過期證據與未知副作用續作。未驗證：並行寫入壓力、長時間運行、多 coordinator、worker crash 接管、取消及真實遠端副作用。這些限制不應被三個小型案例的通過結果掩蓋。
