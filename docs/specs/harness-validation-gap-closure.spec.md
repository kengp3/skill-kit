# Harness 驗證缺口補完規格

日期：2026-10-25（Asia/Taipei）。狀態：使用者已核准驗收邊界及 G00–G09 拆分，並明確排除 G08 Windows。本文為本地實作與驗收依據，未執行項目不視為通過。

## Problem Statement

0.3.0 已有來源實作與 A–G 行為證據，但正常持久信任、真正未知 child 啟動、原生事件重入、移轉中斷、Desktop 操作及部分強度負例仍缺直接證據。原 tickets 的 done 未直接呈現驗證完整度。使用者指定 demo-002 作為獨立驗收目標，要求依 Matt 流程繼續實作與驗收。

## Solution

先鎖定候選與兩個工作區現況，將各細分情境狀態分開；在 demo-002 完成正常接入，故障情境使用其自有可丟棄副本。保留原始事件、合約及成果，逐項核對是否足以支持通過；缺少能力時保持受阻並給出最小解鎖條件，其他工作繼續。

## User Stories

1. 作為使用者，我要保留既有未提交工作，讓補驗不覆蓋其他成果。
2. 作為維護者，我要分開辨識來源實作完成與行為驗證完成，讓 done 不掩蓋缺口。
3. 作為驗收者，我要從凍結候選安裝並核對實際載入版本，避免誤測舊版。
4. 作為 demo-002 使用者，我要先建立該專案自身文件規範，再初始化 harness。
5. 作為使用者，我要 project-setting 單獨可用，只有明確包含 harness 才設定其能力。
6. 作為使用者，我要以模型完成核心流程，選配驗收控制器不成為 runtime 前提。
7. 作為驗收者，我要最小正常任務完成成果與唯一合約，先建立可用基準。
8. 作為使用者，我要移轉命令遭真正中斷後先查明原程序與檔案，再明確續作。
9. 作為使用者，我要三個刪檔門檻仍成立才清除舊設定，歷史產物維持原位與內容。
10. 作為驗收者，我要正常審閱精確 hook 定義後跨 invocation 保留信任，不用 bypass 冒充。
11. 作為使用者，我要 strict 推理強度限制在指定範圍生效，不合格派工保持未完成。
12. 作為驗收者，我要分清 provider、host、schema、認證及模型不可用錯誤。
13. 作為使用者，我要未知派工先查原 child 狀態，不因 timeout 或通知遺失重派。
14. 作為驗收者，我要把 client transport 故障與主責 spawn 回應遺失分開取證。
15. 作為使用者，我要恢復或重複提醒沿用同一合約，不重播副作用。
16. 作為驗收者，我要同事件重入有 native redelivery 依據，不把新 prompt 或 shell replay 當通過。
17. 作為 Desktop 使用者，我要真正停止按鈕與模型選單操作有畫面及宿主證據。
18. 作為使用者，我要 Stop 後先確認既有程序與副作用，沒有明確續作就不接手。
19. 作為維護者，我要已有測試與審查指引可防止同類錯誤，並能直達當前驗收證據。
20. 作為使用者，我要 Windows 明確排除，不耗用本輪資源或當作測試通過。

## Implementation Decisions

### S1. 唯一驗收邊界與狀態

使用者已核准「明確啟用技能 → 原生宿主／模型 → 設定、合約與成果 → 讀回證據」。維護者控制器只控制已指定的故障邊界，不代替模型或預填 observed 結果。

以既有中央驗收表記錄各細分項：實作狀態、驗證狀態（未執行／通過／失敗／部分／受阻／排除）、候選與環境、證據、阻礙及下一步。任何必要分支未通過，整體補驗維持未完成。排除須有本次使用者依據，不能將能力不足自行改成排除。

### S2. 候選、現況與專案接入

執行前保存產品與 demo 的 HEAD、既有變更、適用指示、可核對檔案指紋與候選 manifest。只操作本任務新增或明確擁有的檔案；原有修改不代為提交或清理。

demo-002 原工作區只做正常接入與無破壞性成果。先由 project-setting 初始化自身規範，按 task-harness 提供的 Markdown 規格設定，主責重讀核對。實際載入來源及版本必須可追溯；未信任 hooks 不阻擋模型接手的正常任務。

使用已凍結 0.3.0 候選，安裝或複製完整技能與資源；驗證不需要 helper scripts。若產品變更，另建新候選與指紋並辨識受影響案例，不覆寫或冒用既有證據。

### S3. 隔離、前置資格與生命週期

故障案例用自有 disposable 根與 state，不對 demo 原資料／應用程序或全機網路注入故障。核對 root、指示、skills／hooks／plugins 來源、writable roots、daemon／Desktop endpoint及普通工具啟動資格。

認證不進版本控制或證據。案例間使用全新狀態；同案例的持久信任、未知 child 查回及同合約恢復則保留 state與身分直到案例終止。只有確認自有模型／工具／子程序已退出、證據已保存，才能清理。觀測逾時不是執行終止。

### S4. V04 移轉中斷

模型在副本走正常移轉。先觀測真正命令開始、自有 PID／token及磁碟狀態，才施加一次中斷；查明原程序退出後明確授權續作，重讀三個門檻，保留歷史產物及已完成操作。

若使用 checkpoint 命中窗口，須明列受控時序，只支持 workflow 命令中斷。不得宣稱已測 syscall crash、斷電、原子寫入或交易回滾。未命中窗口的嘗試保留真實判定。

### S5. V01 正常持久信任

正常人工介面審閱精確 hook 定義，分開 project trust與hook trust；不使用 bypass或直接寫信任資料庫。保存來源、hash、信任狀態與實際注入，退出後同 state 的新 invocation再驗證。人工尚未完成時只阻擋該案例。

### S6. V07 強度負例

strict 兩案：僅首選限制且有合格後續候選；全部派工限制且無合格候選。前者實際派工符合指定範圍；後者保留 blocked、無違規派工且無相依成果繼續。

獨立唯讀 probe選 protocol 可表達、模型 metadata不支援的強度，核對實際拒絕層。只有真 upstream error支持 provider負例；host自動修正、schema拒絕、認證失敗等分別記錄。不能繞過產品 preflight 或修改宿主換取假通過。

### S7. V02 未知派工

持久唯讀 child使用唯一 case身分；client transport中斷後由同state查回原child、turn終態與成果，確認無重派。正確處理來源過濾、分頁及 notLoaded／idle語意。

真正主責 spawn回應遺失須在該結果交付邊界有可控故障與旁證；client通知遺失或換連線不能替代。provider網路故障另有精確連線範圍及原始錯誤。缺少能力時相關分支保持受阻，不盲目重派、不修改全機網路或新增必要代理。

### S8. V03 來源、提醒與重入

同合約、一次寫入成果分別經真startup／resume／compact，核對事件、輸入來源、提醒及成果。canonical passive Stop不產生新授權。

完整native re-entry必須有可關聯原邏輯事件的redelivery證據。相同payload、兩個handlers、另一prompt或shell replay只作對應的補充測試。無可用重入介面時保留受阻，不自行擴大產品承諾。

### S9. V05 Desktop

在與本案workspace／state可分清的Desktop驗收環境，實際點停止與選擇模型。停止須命中已開始的無副作用工作並核對程序。模型切換須先有舊worker，後續授權派工核對新繼承及舊worker不重啟。畫面選擇與API證據互相支持，不能互相代測。

### S10. 收尾與維護

完成獨立 Standards／Spec審查、修正required findings，中央報告與tickets一致，README可直達目前證據。以最小維護檢查沿用既有unittest，不把真模型、人工信任或UI資格冒稱CI通過。

日常入口升級與全域操作不是專用驗收catalog的副作用。只完成本案授權範圍；入口仍舊版時單獨回報，不把新候選存在說成日常已升級。

## Testing Decisions

- 每個具名情境採 expected → observed → raw evidence → verdict，保留未命中、控制器錯誤、受阻與未知結果。
- 最小正常成果、字節保留、唯一合約、真事件／PID、實際child身分與模型context為主要證據；checker驗證已有證據，不替代真實試驗。
- 沿用已有設定I/O、Stop與模型生命週期案例的高層邊界，避免重建框架。
- 工具、控制器或來源新增非瑣碎分支時，在已核准邊界保留red → green證據及相稱測試；文件-only變更檢查連結、狀態與來源一致性。
- Windows依最新使用者指示明確排除。不存在的Windows資格不計未完成必要門檻；原歷史skip記錄保留。

## Out of Scope

- Windows情境；記錄G08排除原因，不執行或冒稱通過。
- 全域安裝、日常auth/config、系統網路、防火牆、managed policy、外部服務、Codex本體修改及新VM佈建。
- 外部issue、push、PR、恢復demo歷史workflow、覆寫既有未提交內容。
- 將選配runtime改成核心需求、多主責／原子exactly-once／任意shell即時終止等新保證。

## Further Notes

依使用者已核准的 G00–G09 工作圖推進，G08明確排除。必要的宿主能力或人工操作缺口保持未完成並回報；這不是縮小驗收要求。完整目標只有在其餘必要分支具有直接證據且審查完成後才算達成。
