# AI code review 決策導向報告

產出或更新報告時使用。預設 Markdown，沿用使用者指定格式與團隊政策；保留以下決策資訊即可，不為簡單審查填滿空白章節。無 PR 的 repo／版本比較仍交付業務與品質結論，不虛構 PR、base/head 或平台狀態。

一般變更以需求符合性與程式品質為主；只有約定保留舊行為時才列行為一致性。不要為新增功能套用嚴格等價，也不強迫無關移轉欄位出現在報告。

## 固定呈現順序

完成深度審查及範圍對帳後產出五章正文，依序為：

1. **基本說明**：本次實際開始日期時間（含 UTC 偏移／時區）、專案名稱與完整本機路徑、目的摘要、執行狀態及簡短 Approve／Request changes／Hold、阻擋／缺口數及第一步。項目各自分列，跨 repo 分列路徑；未知填未知，不將多個情境塞在同一格。
2. **範圍說明**：branch/ref 與固定 base/head、比較語意、diff 數量／檔案類型、納入／排除及關聯查閱範圍。正文用分組摘要及例子；完整清單一律放報告最末端並提供入口，不因檔案少而改放正文。
3. **關聯與流程**：變更目標、實際前後作用、依分析結果選擇的圖及影響邊界。先簡述每張圖要回答的問題與選圖理由，再呈現圖；類別、流程／活動、循序、狀態或其他 UML／關係圖均可，無固定必畫組合。圖由已分析所有目標歸納，附固定來源與證據種類；不得用 class 條列取代關係。來源不足要標缺口。
4. **審查結果與問題**：先列所有尚存 F/Q/U 的 ID、狀態、影響、是否阻擋、推薦方案及解除條件，接著逐項詳解；已查面向與證據／不適用理由放在問題之後，避免讓查核清單擋住待辦。逐項詳解優先「位置 → 原始短碼 → 建議修改碼與註解 → 必要原因／觀測／解除說明」，不先用長篇文字淹沒程式碼。非程式或無可靠 API／契約時可用文字，但須說明為何。無問題明說約定範圍未發現阻擋，不硬湊 finding。
5. **結論**：重申該版本與範圍的建議、未解除 ID／必要缺口及按順序的下一步與重審門檻。與首頁一致，不新增正文沒提過的阻擋，不擴大成全 repo 正確。

結論後可放證據附錄（指令、log、hash、來源與規則等），**最後一節必須是完整檔案清單**：所有 diff 路徑、舊／新路徑、狀態、符號或責任、差異作用、分析結果／finding 或缺口；關聯但未修改的來源另表。二進位、生成檔、工具失敗、未讀及排除項皆列狀態與理由。完整清單是盤點結果，不是只列檔名即宣稱已審。

首頁仍保留會改變判斷的限制；完整 commit／遠端可放範圍或證據附錄。時間是本輪審查開始時間，不是「審查期間」或 commit 時間；沒記錄就如實說明。只改排版不重設執行時間；重審沿用測試時另記觀測版本及時間，不冒稱重跑。必要步驟未完成時可交付部分完成報告，不能標為完整或通過。

## 易讀性：讓讀者先找到待辦

- 基本說明先呈現建議、尚存問題及第一步，再列專案、執行時間與目的。路徑用有意義的短連結文字，完整路徑留在連結目標或附錄；精確版本、時間記錄限制及工具細節分組置於範圍／附錄，首頁仍保留會改變決策的限制。
- 問題總表的 ID 連到詳解，首頁提供問題與範圍入口。使用 Markdown 標題產生的章節連結並核對實際目標；不要為了導覽在正文插入獨立的 `<a id="...">`。若檢視器不支援標題連結，保留清楚的章節名稱／ID 或改用可定位的檔案連結。正文以「已確認缺陷／待釐清／必要證據缺口」稱呼事項，首次使用 F/Q/U 或其他縮寫需解釋；不要求讀者先懂內部代號。
- 每項問題保留一個可理解的具體例子：初始資料與操作、預期、實際、影響。案例名稱不是輸入；金額寫明單位，必要時用小表比較。細節與更多案例放證據附錄，來源連結直接定位相關方法或紀錄。
- 共同的重驗要求集中寫一次，各問題只列專屬解除條件；不把同一限制、完整雜湊或工具自述重複貼滿正文。證據可用具體檔案連結保存，不能因精簡刪掉必要未知或阻擋。
- 同方法多項修法需交代套用順序與相依，必要時給一份整合修改碼；無需重貼等價片段。無缺陷報告簡述查核結論與證據，缺證報告直接說補哪個紀錄、如何判定補件合格，不硬造程式修法。

## 圖表：說明關係與證據邊界

優先使用 Markdown 內的 Mermaid，依問題選圖，不固定每份報告的圖數。單一局部問題無需硬湊全系統圖；來源不足時明列缺口，只畫已確認部分。若輸出環境不支援圖形，提供帶方法／資料標籤的文字呼叫鏈，明示限制。

先從變更目的、風險及影響分析列出讀者必須理解的問題，再選圖；以下為選擇依據，不是每次都要填滿的圖表清單：

| 分析結果／要回答的問題 | 適合的圖 | 圖中必須保留的資訊 |
|---|---|---|
| 類別職責、介面、繼承／實作、依賴或擁有關係有變動 | UML 類別圖；非 OO 程式用模組／函式關係圖 | 變更責任、關係方向及種類；只列相關成員，不把方法執行順序畫成繼承。 |
| 條件分支、驗證、業務步驟、錯誤處理決定結果 | 流程圖或 UML 活動圖 | 入口、條件、正常／拒絕／例外出口、重要副作用；跨責任可用泳道。 |
| 跨類別／服務互動、交易、回呼、非同步或並行順序影響正確性 | UML 循序圖 | 參與者、訊息方向、條件／迴圈／並行片段、提交或失敗時機；無法證明的先後不畫成必然。 |
| 訂單、付款、任務等生命週期或合法轉移有變動 | UML 狀態圖 | 初始／終止狀態、事件、轉移條件、轉移效果及不合法轉移。 |
| 模組邊界、外部依賴、執行節點或部署責任影響範圍 | UML 元件／部署圖或有標示的架構關係圖 | 系統／信任／執行邊界、依賴與資料方向；不憑空推定部署拓樸。 |

其他圖型也可，只要能回答實際分析問題並有來源支撐。一張圖已足夠就不加圖；若結構與時序各自影響判斷，可搭配類別圖與循序圖。圖說以一句話交代「因本次變更涉及 X，使用 Y 圖說明 Z」，不必逐一列出未選的圖。流程圖／一般架構圖不冒稱為嚴格 UML；Mermaid 無法表達必要語意時改用可用表示法，或明示簡化與限制。

例如 TaskGroup 的 opened／cancel 競速，優先選循序圖呈現兩執行緒交錯；只有類別職責或相依變更也需要解釋時才另加類別圖。單純狀態轉移規則則優先狀態圖，不因專案使用 Java 就固定畫類別圖。

- 關係圖回答「誰呼叫誰、傳什麼資料、哪裡影響結果」；循序圖回答「何時驗證、更新、失敗或還原」。節點標責任，箭頭標方法／資料與方向，標題說明範圍；有特殊線型或顏色時附圖例，不只靠顏色表達證據強弱。
- 呼叫關係與執行順序分開畫：A 先呼叫 B 再呼叫 C，不畫成 B 呼叫 C。流程圖可串接操作，但節點需標明呼叫者與操作；不同版本的查詢／副作用順序不合併成一條含糊路徑。提交證據缺漏等審查狀態放圖旁註記，不接成程式執行步驟。
- 舊／新用分區或獨立圖表示。規則映射與實際呼叫分清楚，不畫成舊系統會呼叫新系統；相同名稱也不是已確認映射。
- 每組關係附固定版本的來源連結；圖旁說明與 finding／未知項的關聯。保留會推翻結論的 guard、條件分支及失敗路徑。省略的細節明示，不能把有條件路徑畫成必然執行。
- 明確區分「來源推導」「實測案例摘要」「執行追蹤」。只跑核心方法不表示其周邊箭頭已整合驗證；只有末端觀測時，不聲稱每個中間步驟都被追蹤。物件別名、不可變新物件與並行關係不得被簡圖誤表示。
- 交付前核對箭頭、時序、來源、案例及圖中結論。可用渲染環境時檢查語法與可讀性；未實際渲染須如實記錄，不以原始碼檢查冒稱視覺驗證。純排版更新保留原執行時間及結果，不必重跑 Java。

## 決策規則

先依約定審查方式與範圍清單標示執行狀態，和業務 PASS／FAIL／UNKNOWN 分開：

| 執行狀態 | 條件 |
|---|---|
| 完成 | 有可審項目，約定審查步驟皆已完成；不表示業務通過，純來源審查仍可能 UNKNOWN |
| 部分完成 | 已有可用審查結果，但仍有必要步驟未完成；連到未完成項及原因 |
| 失敗 | 有待審項目，但本輪無可用審查結果；保留失敗原因與恢復所需資料 |
| 無可審項目 | 選取後沒有項目；列排除理由，不以零問題宣告 PASS 或 Approve |

執行狀態以開始時約定的審查義務為準，不能改稱「資料包已讀完」來覆蓋未完成的必要驗收。若約定只做來源審查，可完成且結果仍 UNKNOWN；若約定需核對完整實跑證據，必要案例／觀測缺漏則為部分完成，即使其餘資料全部讀過。

例如 10 個必要項已完成 8 個、2 個工具失敗，執行狀態為部分完成。若已有有效阻擋，仍為 FAIL／Request changes；否則為 UNKNOWN／Hold。不得藉事後縮小範圍將未完成改成完成。非必要的額外檢查失敗列限制，不自動讓已完成的約定範圍永久暫緩。

| 依序判斷 | 合併建議 |
|---|---|
| 有有效、未解除的阻擋問題 | Request changes（要求修改），其他未知仍保留 |
| 無上述問題，但必要證據缺漏／過期或約定審查未完成 | Hold（暫緩），列具體補證 |
| 約定範圍已完成，必要證據有效且沒有未解除阻擋 | Approve（建議通過），列明例外及非阻擋事項 |

必要證據須關聯本次範圍、規則與風險，不因範圍外未知永久 Hold。已確認本次變更造成必要測試失敗可構成阻擋；未執行、環境故障或不明原因不自動當程式缺陷。修正已知問題的證據失效時，不提前放行；目前無有效反例則 Hold，有其他有效阻擋則 Request changes。

嚴重度沿用團隊定義；未定義時描述影響，不憑空制定 P2 自動拒絕政策。純偏好不阻擋；既有問題標示歸屬，只有適用政策或本次風險確實要求才阻擋。移轉契約未核准的差異可阻擋，即使新版是品質改善；有意設計差異不一律稱 bug。

報告建議不表示已提交 review 或平台已禁止合併。平台動作寫實際狀態，未查合併規則寫「未查核」。GitHub 使用 Comment／Approve／Request changes；Hold 可用 Comment 說明，但 Comment 本身不擋合併。需要強制門檻時指出必要審查／檢查設定缺口，不自行改設定。要求修改不等於關閉 PR。

## 問題：可定位、可查證、可結案

同根因合併呈現，保留受影響案例及位置。finding 使用穩定 ID（如 F-001），不把嚴重度或阻擋狀態編進 ID；重審延用 ID。必要證據缺口另用 U-001 等，不冒充已確認缺陷。

每項 finding 提供：

- **標題與歸屬**：觸發條件＋錯誤效果；本次新增、加劇、既有、契約差異或環境問題。
- **獨立判斷**：嚴重度與具體影響、證據種類及假設、是否阻擋與理由、處理狀態。不要用總分或信心百分比取代。
- **位置與規則**：固定版本、檔案連結、class（類別）、method（方法，含參數型別以區分多載）、問題行號及摘錄範圍，另列 Rule ID／規格／測試依據；跨 class 分清根因與受影響呼叫位置。非物件導向程式用實際模組／函式，不適用欄位省略。PR diff 連結只用已核對位置，圖外來源可用 commit permalink。
- **觸發與結果**：輸入、初始狀態、相關設定、操作序列，以及預期／實際差異、受影響者。
- **契約適用性**：明示公開 API 或業務入口的驗收邊界、觸發可達性及依據；推定契約下的條件式阻擋與已確認 PR 阻擋分開。上游防護排除案例時，同步修正問題摘要與決策，不能只在附錄補一句限制。
- **證據**：實跑提供命令、退出碼與原始產物；來源推導提供完整路徑與前提並明示未執行。不要求每個確定缺陷都有可執行重現；猜測列 question／調查項，不能冒稱已確認。
- **反證查核**：簡述已核對的 guard／caller／設定，以及為何仍無法避免該觸發；來源不可得則標明尚未排除的前提。無證據不要填「已排除所有可能」。
- **修正與解除**：給一個具體推薦方案，說明改哪個責任點、為何能解決及適用前提，再列需要成立的行為與驗證；只有契約或架構取捨確實不同才補替代方案，不只寫「請確認／修正」。容許等效方案。若考慮改契約，須有權決策者明確核准及相關驗證，不由 AI 授權例外。

必要缺口寫明「缺什麼 → 無法判斷哪條必要規則 → 最小補證方式」。責任人只有已知才填，否則待指派。非阻擋建議明示 optional／nit／FYI，避免作者把每則評論都當必改。

## 程式碼對照：讓讀者在報告內理解原因

每項程式缺陷依序呈現「精確位置 → 有問題的短原碼 → 建議修改碼與註解 → 必要原因、觀測及解除條件」。在程式區塊前明示問題行號與關鍵運算；摘錄保留足以支持判斷的上下文，不只給行號或貼整個 class。摘要表以 ID 連到詳解，避免重貼程式。

- 優先展示被審版本的問題片段；需要基準才能理解原因時再補舊碼。新舊對照按同一業務規則排列，不強求同名方法或一對一檔案；跨 class 時列必要片段及呼叫／資料關係。
- 每段標明舊／新、已審版本、完整檔案路徑與行號，提供固定來源連結。可在段落上方共用已明定的完整 commit。從該版本原樣擷取；分段摘錄分別標行號，省略處明示，不拼成看似完整的方法。
- 每項問題要讓讀者沿原碼追到影響結論的變數：顯示參數／欄位或本地變數的宣告與初值、關鍵賦值或轉換、相關 guard，以及造成結果的使用或副作用行。連續不長時展示這段完整原碼；中間很長且確實無關時，按真實行號拆成多段，在程式區塊外標出省略範圍與理由，保留每段原樣，不把 `...` 或新增解說註解混入原始碼。跨方法／class 的值或副作用也要展示必要的來源片段與呼叫關係；已在同份報告完整展示的片段可直接連回，無須重貼。
- 保留影響結論的 guard、容器初始化、例外處理及相關設定；可省略無關內容，不能截掉會推翻 finding 的脈絡。若來源無法取得，明示缺口，不編造程式碼。
- 分開標示「原始程式」「實際觀測」「建議修法」。新增註解、簡化示意或擬議修正不得冒充原始碼；未執行的修法不得稱已驗證。
- 建議修法優先提供可定位的最小程式碼或 diff，搭配簡短註解說明修改原因與需保留的行為；標明替換／插入／移除位置。涉及順序時保留必要前後操作，跨問題合併修法列出涵蓋 ID。只有缺少必要 API／來源、需先決定契約或屬非程式問題而無法可靠寫碼時，才改用純文字，並說明原因及具體下一步；不虛構 API 或可直接套用的實作。
- SQL、設定或缺少實作造成的問題，引用對應來源或已查閱範圍，不硬湊兩段 Java。純偏好事項可只提供精確位置。證據缺口標示「相關程式位置」，另定位缺少的紀錄／欄位，不將正確原碼標成問題碼或要求無依據的程式修正。

交付前逐段核對摘錄與已審版本，確認解釋、測試結果及 blocking 理由能連成可查證的因果關係。程式碼對照補充證據，不取代原始輸出與驗收條件。

## 修正與重審

狀態可用 open、fixed-pending-verification、verified、accepted-exception、false-positive。作者宣稱修好或按 resolved 不等於 verified；核對新版本與受影響證據後才結案。若後續證據推翻 finding，記錄理由並標 false-positive，不留下無根據阻擋。

版本、base、契約、設定或 runner 改變時檢查影響範圍，重驗必要證據；保留舊結果但標明不適用目前版本，不重算 hash 冒充重跑。來源推導型品質問題可由更新後的推導解除；移轉的業務一致性 PASS 仍遵循 [migration.md](migration.md) 的證據門檻。核准例外保留決策者、來源、規則及允許差異，只解除其明列範圍。

附錄保存本輪實際採用的技能、reference、專案規則與工具路徑及版本／hash，注明用途；不以目前檔案 hash 冒充歷史載入版本。模型標籤可取得才填，否則未知。中斷後續作須核對這些依據，保留原始證據索引與未完成項。

分別判斷「原始執行證據」與「審查結論」能否沿用：前者核對原碼、案例、契約、runner、相依及環境；後者另核對生效規則、政策與判斷前提。只改排版不必重跑程式；政策改變可先重判既有觀測，若需要新輸入或觀測再補跑。helper 版本變動而拒絕舊 manifest 時，保留舊證據並依新版重新取證，不能改 hash 偽造成功驗證。

## 交付前：用讀者角度核對實際報告

先核對五章順序與完整清單位於最末端，再只讀基本說明、短決策及第四章總表，能否知道結果、所有尚存事項、現在先做什麼？檢查每張圖的選圖理由是否對應分析結果、是否漏掉影響判斷的時序／狀態／邊界、是否有重複或無作用的圖。逐項對照正文與證據，確認 ID 無遺漏、同根因未重複計數、阻擋理由一致，並能從位置、原因、推薦動作走到可驗證解除條件。未確認的契約先給決策題及記錄方式，不羅列多個修法讓讀者猜。

發現缺陷先修報告並重新核對；只有來源、輸入或觀測改變才重跑相關執行。記錄查出問題、修正及仍有限制，不以模板驗證通過代替閱讀查核。有技能修改授權時將可重現缺陷回饋到最小相關指引，重新套用驗證；沒有授權則回報改善建議，不自行修改安裝技能。
