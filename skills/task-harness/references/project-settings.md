# Task Harness 專案設定規格

本文件由 task-harness 維護，供 project-setting 依規格執行初始化、更新、移轉及修復。提供本文件、已確認專案根目錄、本次授權與診斷結果；設定後由 task-harness 重讀並檢查。主要由模型判讀，不要求解析器、runtime script、CLI 或 MCP 服務。

## 啟用與唯一來源

- 僅在使用者指定包含 task-harness，或明確啟用本次任務後由其委派設定時套用。project-setting 單獨使用不需本文件，也不加入本設定。
- 專案長期設定只存根目錄 project-setting.md。不要另建 harness-project.json、JSON 設定區塊或重複路徑欄位。規格與範本不是另一份專案實際設定。
- 一次任務的模型指定、替代安排及實際執行結果記入同一份任務合約；恢復同一任務仍有效，新任務不沿用。只有明確要求設為專案預設才修改此檔。

## 文件位置

在現有「類型／文件用途／目的地與檔名」表新增以下兩列；既有列與其他內容保留。這兩列是唯一的合約／收據位置來源，不在 Task Harness 表另填 contract_dir、receipt_dir 或 project_root。

| 類型 | 文件用途 | 新專案預設目的地與檔名 |
| --- | --- | --- |
| task-contract | 任務合約與可恢復狀態 | docs/plans/{slug}.task-contract.md |
| hook-receipt | 實際 hook 事件的技術收據 | docs/research/{slug}.hook-receipt.md |

上述路徑只在沒有既有位置或自訂要求的新初始化使用。已有位置必須沿用，移轉不搬移或重新命名產物；既有分類列與舊設定不一致時先回報衝突。解析模板後的實際目的地須在確認根目錄內，不得越過符號連結、`..` 或內部／第三方目錄邊界。兩種類型不得指向相同的實際產物。

不因初始化預建空目錄或假收據。只有觀測到真實 hook 操作才保存技術收據；模型主動檢查只更新合約，不假造 hook 事件。

## 固定設定表

在唯一的二級標題 `Task Harness` 下維護一份「設定項目／值」表。表格列順序及欄位周圍空白可以調整；標題、兩個欄位名稱與設定識別字按本規格使用。

| 設定項目 | 值與有效性 |
| --- | --- |
| schema_version | 必填，值為 `1`；其他版本須由相應規格處理，不當成本版成功讀取 |
| model.default | 選填，專案預設候選模型清單；省略表示沒有專案預設 |
| model.stage.<階段名稱> | 選填，該階段的候選清單；四個預設名稱為「規劃、執行、驗證、審查」，也可使用自訂階段 |
| model.role.<角色名稱> | 選填，該 agent 角色的候選清單；名稱與任務實際採用的角色一致 |

階段與角色名稱為非空字串，前綴後的完整字串就是名稱，不將名稱中的句點當另一層設定。名稱、模型與強度不得含換行或表格分隔符；候選中的模型與強度也不得含 `,`、`;`、`[`、`]` 等清單分隔符。角色／階段列可省略，不要求每個任務走完全部階段，不預綁模型。

模型值採 `[模型A;high, 模型B;medium]`。逗號分隔候選，分號連接模型與 reasoning effort；第一項為首選，其後依序替代。可省略分號與強度，如 `[模型A;high, 模型B]`，未指定者使用宿主對該模型的預設強度。候選與分隔符周圍空白忽略；清單內順序影響行為。這是設定語法；格式正確的候選即使目前不可用，或宿主不支援其強度，也不是設定格式錯誤，應交由模型選擇／回退流程處理，不要求 project-setting 改寫。範例不代表預選或保證宿主支援任何模型。

省略整列表示未設定；空值、空清單、空候選或空強度不是未設定，依修復流程處理。`default` 可作最後一項且不附強度；無論有無填寫，末段預設回退都自動生效。清單重複模型不重複嘗試，執行順序與強度處理由模型分工規則決定。

## 初始化、讀回與有效性

1. 確認根目錄、授權、現有分類表與 Task Harness 區段。無設定且已授權初始化時，交由 project-setting 先建立其文件規範，再合併本規格的兩列與 `schema_version`；可使用 [最小範本](../assets/project-settings.md)。不要將範本整份覆寫到既有檔案。
2. **舊設定或修復**：存在 harness-project.json、移轉中斷、缺欄／重複／無效設定時，讀取 [移轉與修復流程](settings-migration.md)，交由 project-setting 依流程處理；新舊衝突先回報。移轉驗證前保留舊檔，不以預設路徑掩蓋缺漏，也不因只有舊檔就默默停用。
3. 讀取兩個必要分類列與設定表，檢查唯一區段、唯一識別字、必要欄位、版本、目的地及候選格式。必要資料缺漏、同一類型／鍵重複或值無效時，列出實際位置與原因；只按規格與原授權修復，不能自行挑一份重複值使用。未識別的本區段鍵保留原文並交回規格核對，不擅自刪除或當成已生效；其他區段不屬本規格。
4. 依本次已授權的接入意圖，按下節的標準 hooks 規格交由 project-setting 合併平台設定；使用者要求維持停用或禁止 hook 變更時，保留限制並由模型接手。
5. project-setting 完成後，task-harness 必須重新讀取實際檔案，核對有效值與無關內容保留，並依分類表定位本次合約後繼續。設定寫入／格式讀回、宿主載入／信任、實際事件及產品驗收分別回報；設定存在不是環境資格。

最小有效設定只有兩個分類列與 `schema_version = 1`。所有模型列省略時，依規則沿用主責當前模型與強度。舊環境資格不得直接寫入為新流程已通過；沒有必要工具或 hooks 時依模型接手流程繼續，而不是修改資格旗標掩蓋缺口。

## Codex 標準 hooks 接入

[Codex hooks 範本](../assets/codex-hooks.json)隨 task-harness 交付，是唯一來源；純複製 skill 安裝可直接取得，plugin 的 hooks 定義也由同一資源建包。只在明確包含 task-harness 的本次接入／修復授權內，將本節及範本提供給 project-setting 操作；不修改全域設定。

1. 先核對目前宿主為 Codex，讀取專案 `.codex/hooks.json` 與 `.codex/config.toml`，並查核本專案已載入的 plugin hooks。若已有內嵌 `[hooks]`，沿用 TOML；同層 JSON 與內嵌定義並存且有效來源不明時先回報，不覆寫或另加一份。其他宿主沒有已確認的接線規格時，回報能力缺口並由模型接手，不直接套用 Codex 格式。
2. 比對已載入來源的事件、完整 handler 定義及 matcher／事件來源的有效覆蓋範圍。三者等效且涵蓋範本的無 matcher 範圍時才沿用、不再加入；plugin 的等效定義即使未信任，也不能藉建立專案副本繞過信任。相同命令若只涵蓋 startup 等受限來源，或覆蓋範圍不明，保留原群組並回報為部分／自訂接入，不能視為已涵蓋 resume、compact 等其他來源。依本次明確授權釐清與修復範圍，不自行擴大既有 matcher，也不盲目新增重疊副本。不同的既有 handler 與無法確定歸屬的內容仍保留。
3. 需要新增時，僅將範本的 `SessionStart`、`UserPromptSubmit`、`Stop` handler 合併到上述唯一專案來源，保留 matcher 群組與其他設定；新 handler 使用無 matcher 群組，不擴大既有 matcher。若宿主使用 JSON，範本的 `hooks` 是合併內容，不整份覆寫檔案。無論是否新增 handler，都按本次啟用意圖核對 `[features]` 的 `hooks = true`；原值為 false 時回報變更，明確要求維持停用時保留原值。
4. 讀回確認新增定義、來源唯一、沒有重複、無關內容保留。按宿主 `/hooks` 正常流程審查／信任精確定義，重新載入後查核事件；需人工信任時回報具體位置，其他工作依模型接手規則繼續。不要自行寫入虛假已信任／已執行旗標，也不要求使用者安裝 runtime。

macOS／Linux 的 command 與 Windows 的 commandWindows 都只用系統 shell 內建 `echo` 傳送固定內容，不插入專案路徑或使用者文字。兩個開始／輸入事件只提醒模型；`Stop` 僅回傳合法空物件 `{}`，沒有條件阻擋或有界補救。模型在四個共用時點主動檢查，並如實區分「已寫入、已載入、已信任、已觸發」。停用時只處理本次可辨識的專案定義，不移除 plugin 以外的無關設定或關閉全域功能。
